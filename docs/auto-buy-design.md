# 全自动购买设计

> **现状（2026-10-23）**：控制台已经简化成三页版（抢购 / 记录 / 设置），
> 一页一个全局价格区间 + 限量 + 预算，不按皮肤名分目标、不再有多目标向导、
> 目标库页、分析页和实时预览流。本文件是**按时间顺序记的设计决策**，
> 里面的界面描述属于当时的版本，现行界面看 `说明.txt`。
> 没被砍掉的设计（余额不足只点取消、倒计时 floor 模型、抢错保护、
> 一页不翻页、不点公示期等）都还在代码里。

用户勾选目标（武器 / 磨损上限 / 价格上限 / 买几件），程序自己去交易行把它买回来。
现状：程序能做到「列表已经在屏幕上时，挑符合条件的买」（`engine.py:265-405`）。
缺的是**把界面操作到那个状态**，以及**买入失败后的处理**。

本文件记录设计决策与未验证项。**未验证的环节先用假 `InputSink`/`Screen` 在测试里跑通，再上真机。**
（注：早期版本有「演练模式」，已于 2026-11 整体移除，产品只剩实战一条路径。）

## 二、每步的失败模式与处理

设计原则：**任何一步不确定就停，并把界面留在可人工接手的状态。**
买错东西的代价远高于没买到。

| 步 | 失败模式 | 处理 |
|---|---|---|
| ① | 不在一级菜单（在局内/设置里） | 停，提示「请先回到大厅」 |
| ② | 标签位置变了 | 模板匹配不到就停，不盲点 |
| ③ | 目录里找不到目标武器 | **滚动到底仍找不到则停**，报「目录里没有 X」；不要继续往下走。滚动参数已实测：项 pitch 114px、一次滚轮 278px、目录按赛季倒序（S11→S2），可按赛季号估算目标在第几屏 |
| ④ | 点目录项后没进列表页 | 超时停 |
| ⑤ | 价格输入框没聚焦，输入的数字落到别处 | 点输入框后**截图确认出现光标**再输入 |
| ⑤ | 筛选面板展开/收起状态与预期不符 | 先判断面板是否已开，再决定点不点「筛选」 |
| ⑥ | OCR 读不出价格 | 该行跳过（已有行为，`market.py:135`） |
| ⑦ | 没有任何一条符合条件 | **翻下一页**（见第四节），翻完仍无则停 |
| ⑧ | 点了购买但没弹确认窗 | 已有超时处理（`engine.py:476-478`） |
| ⑨ | **余额不足** | 立刻停，**绝不点「充值」** |
| ⑨ | 商品已被别人买走 | 退回列表换下一条 |

## 三、必须新增的安全设施

1. **余额不足弹窗处理**（已实现：`core/popup.py` + `engine._guard_insufficient`）
   录屏实测：「您当前的三角币不足，是否前往充值？」，弹窗有「取消」和「充值」两个按钮。
   **程序只允许点「取消」**，然后停止并报告。点「充值」会花真钱，属于不可逆操作。

   实现要点（每一条都有对应测试，见 `tests/test_popup.py`、`tests/test_engine_insufficient.py`）：
   - 判据是正文里的「三角币不足」四个字，不是模板匹配 —— 弹窗底色和确认弹窗太像，
     模板会互相命中。
   - `popup.cancel_point()` 是**唯一**对外暴露的点击点，它只返回「取消」。想点充值
     必须绕过这个函数，代码评审时一眼能看见。
   - 认出了弹窗但没定位到「取消」时**返回 None 并停手**，不退回任何默认坐标 ——
     默认坐标很可能落在「充值」上。
   - 命中后中止整场，不是换下一条商品：余额不足是账户级问题，换哪件都还是不足。
   - 缺多少币那行小字 OCR 读不准（实测 `2,001` → `2 ， 〔 〕 1 〔 〕`），
     读不准就报 `None`，不猜 —— 猜出的「21」会让人以为只差一点而反复重试。

2. **筛选状态标记**
   筛选应用后按钮显示「已筛选 1 项」。程序开始前应检查是否已有残留筛选
   （上次失败留下的），有就提示用户先清掉。

3. **买错保护**
   点进详情页后、点购买前，**再确认一次详情面板里的商品名与价格**符合条件。
   列表页的 OCR 可能出错，详情页信息更完整（含精确磨损值 `0.808755`，见 §4.7）。

4. **购买次数上限**
   单次运行最多买 N 件（用户设定），防止筛选条件写错时连续买入。

### 4.8 真机实测：鼠标点击在独占全屏下完全无效（2026-10-20 实测）

游戏窗口开着、大厅界面确认无误、坐标也核对过（交易行 x 689-735 / y 43-58，
和录屏实测的 688-736 / 47 一致），但**点不动**。逐项排查结果：

| 检查 | 结果 |
|---|---|
| 游戏窗口尺寸 | **1936×1119**，比桌面 1920×1080 大 → 独占全屏 |
| `SetCursorPos(712, 50)` | 无效，光标纹丝不动 |
| `SendInput` 相对移动 20×(+10,+10) | 无效 |
| `mouse_event`（旧 API） | 无效 |
| `SendInput` 绝对坐标 | 无效 |
| 光标可见性 | `flags=1`（显示），位置固定在 (1345,545) |
| DPI | 96，坐标无缩放 |
| 会话 / 桌面 | session 1、Default 桌面，与游戏同会话 |
| 权限 | 游戏与我都是非管理员，无 UIPI 隔离 |

**根因是光标被裁剪锁（ClipCursor）**：`GetClipCursor` 返回整屏矩形，
但光标被钉在一个点上。手动执行 `ClipCursor(None)` 之后，`SetCursorPos`
立刻恢复正常（实测三次移动全部 OK）。

结论与对策：

1. **项目启动时必须先 `ClipCursor(None)`**。否则整个点击链路静默失效 ——
   `SendInput` 照返回成功、`GetCursorPos` 照返回坐标（但坐标是假的），
   表现就是「程序说点了，游戏没反应」。
2. **`Mouse.click(verify=True)` 的坐标校验在全屏游戏下会误报**。
   实测 `GetCursorPos` 返回的是被锁住的位置，不是 `SendInput` 设的位置，
   于是 `MouseStolen` 被误触发。这条校验是为窗口化场景写的，
   独占全屏下应当关掉，或者改成「点击后校验画面变化」。
3. **独占全屏下合成输入（SendInput / mouse_event）对游戏无效**。
   实测三种方式全都不动光标。游戏要吃 Raw Input，而 Raw Input 只认真实
   硬件事件。可行路径只有两条：
   - 让用户在游戏里把显示模式改成**无边框窗口化**（Borderless Windowed），
     这是大多数同类工具的标准要求；
   - 或者改用驱动级输入（如 interception 驱动 / 虚拟 HID），
     但那是另一个量级的工程，且可能触发反作弊。

**在解决第 3 点之前，这个项目的「自动点击」在独占全屏下不可能工作。**
识别部分（OCR、列表解析、弹窗识别）全部正常，可以离线用录屏帧验证。

#### 复位：从任意页面回到市场

用户点「开始」时可能停在任意位置。硬编码「从大厅按 F4」在那种情况下
会失败——实测起点在在售页且面板开着，F4 只开不关所以毫无反应。

`Navigator.recover()` 分两种情况：

| 起点 | 动作 | 理由 |
|---|---|---|
| 已在市场 | 不动 | — |
| 大厅 | 按 F4 | **不能按 ESC**——大厅按 ESC 会弹出退出菜单 |
| 市场内其它页 | 连按 ESC（最多 3 次） | ESC 只关面板/退页面，不会点到按钮 |

实测退出序列：`filter_onsale --ESC--> detail --ESC--> market`

如果 ESC 退过头到了大厅，会再按一次 F4 重新进市场。

#### 三个致命坑

**① 复选框要点方框，不是文字。** 早期按文字中心算（x=718/867/1105/1354），
实际方框中心在 **x=580/818/1058/1296**，差 20-80px，点了全部无效。判据用
「框内亮像素」：空框 0-60，勾上 300+。**不能用画面变化率**——0.04% 的变化
可能只是光标划过。

**② 下拉项的热区 = 文字顶部 - 16。** 逐项验证 5 个选项全部命中：

| 项 | 文字顶部 | 点击 y | 结果 |
|---|---|---|---|
| 棱镜攻势 | 422 | 406 | ✓ 下拉框显示「棱镜攻势」 |
| 美杜莎 | 470 | 454 | ✓ 「美杜莎」 |
| 电玩高手 | 518 | 502 | ✓ （OCR 空，但已收起） |
| 命运王牌 | 565 | 549 | ✓ 「命运王牒」（OCR 认错字） |
| 气象感应 | 613 | 597 | ✓ 「气獠感应」 |

热区只有 ±8px 宽，差 4px 就点空。**早期用 -12 / -14 全部点空**，一度误判
成「滚动惯性导致热区漂移」，其实是偏移量一直不对。

**③ 验证读下拉框，不读面板外的筛选标签。** 面板开着的时候，页面顶部那行
「筛选中-xxx」被面板盖住，OCR 读不到 —— 早期据此判「读不到就按成功处理」，
等于没有校验（实测放过了一次选错项：偏移越界点到「棱镜攻势」）。

收起态下拉框在 y≈327 / x584-640 显示选中项，这个位置**不会被面板遮挡**。
OCR 会认错字（「命运王牌」→「命运王牒」、「气象感应」→「气獠感应」），
所以判据是「目标里至少一半的字出现在读到的串里」，不要求整串相等。

#### 赛季下拉的选项是**皮肤系列名**，不是赛季号

实测 **12 项**（2026-10-20 完整枚举，逐屏滚动 + 2x 放大 OCR）：

| # | 系列 | # | 系列 |

| 1 | 全部赛季 | 7 | 棱镜攻势S2 |
| 2 | 棱镜攻势 | 8 | 悬赏令 |

| 4 | 电玩高手 | 10 | 造物纪元 |
| 5 | 命运王牌 | 11 | **群星** |
| 6 | 气象感应 | 12 | 疾光魅影 |

用户说的「赛季」在这个界面就是**主题系列**。配合勾「传说品阶」+ 确认，就能
得到该系列的全部传说皮肤。

**浮层默认不在顶部**：刚展开时首项是「棱镜攻势」，「全部赛季」要向上滚才
看得到。滚动锚点必须是**第一项的位置 (613, 380)** —— 早期用 y=450 落点不
对，滚了完全没反应，据此误判成「浮层不支持滚动 / 向上滚无效」。

**滚一格移约 3 项**，滚到第 3 屏（`棱镜攻势S2` 打头那屏）就到底，再滚画面
完全不变。所以 `col_pick_season` 用「这一屏的可见项和上一屏完全相同」判到底，
不空转。

**下拉不支持键盘导航**：按一下 DOWN 浮层直接关闭（实测）。只能靠鼠标点。

#### 热区位置和字长有关（两个坑，差 24px）

| 字长 | 例子 | 文字顶部 | 可点热区 | 偏移 |
|---|---|---|---|---|
| 3-4 字 | 棱镜攻势 / 美杜莎 / 电玩高手 / 命运王牌 / 气象感应 | 422/470/518/565/613 | 406/454/502/549/597 | **-16** |
| 2 字 | 群星 | 588 | 576-616（中心 596） | **+8** |

早期只测了 3-4 字的长项，把 -16 当成通用规律，结果「群星」怎么都点不中
（+8 才对，用 -16 会点到上一行）。现在偏移表覆盖整行：`(-16, 8, -12, 12,
-8, 16, -4, 20, 0, 24, -20, 28)`。

**读完 y 之后要重读一次再点**：滚动有惯性，刚滚到底时读到 y=588，浮层可能
还在动几像素，直接用旧 y 点会落到相邻行（实测「群星」588+8=596 点中了
「电玩高手S2」）。

#### OCR 必须先放大 2 倍

浮层选项是 15px 高的灰字。**原尺寸下 WinRT 会整行跳过笔画少的短项** ——
实测「群星」两个字被完全漏掉：原始 OCR 从「造物纪元」@540 直接跳到
「疾光魅影」@635，中间 y≈588 一个词都没有，但像素上明显有字（亮度
21.9 → 29.3）。

放大 2x（INTER_CUBIC）后能正常读出「群星」。3x/4x 反而因为插值过度变糊，
**2x 是实测最稳的**。`_season_items` 里所有坐标都要 `//2` 换算回屏幕坐标，
`_phrases` 的横向间距阈值也要 ×2。

#### 校验必须读下拉框本身

面板开着的时候，页面顶部那行「筛选中-xxx」被面板完全盖住，OCR 读不到。
早期据此判「读不到就按成功处理」，等于没有校验 —— 实测放过了一次误选
（点「群星」实际选中「电玩高手S2」，下拉框当时读不到，于是当成成功，
最后筛出错的皮肤）。

收起态下拉框在 **y≈327 / x584-640** 显示选中项，这个位置不会被面板遮挡。
OCR 会认错字（「命运王牌」→「命运王牒」、「气象感应」→「气獠感应」），
所以判据是「目标里至少一半的字出现在读到的串里」。

**读不到就返回 False**，宁可重试一轮，也不能带着错的筛选条件往下走。

#### 复位不能用 ESC

ESC 有时只关浮层、有时连整个筛选面板一起关。复位动作固定成「再点一次
下拉框」（点一下开、再点一下关），关完用 `_panel_open()` 确认面板还在
（不能用 `where()`：浮层收起后下拉框显示的是系列名，页面锚点对不上，
`where()` 会误报 unknown）。

#### 三个「状态判据」的坑（2026-10-20 全部实测）

这三处都是「看起来能判、实际误报」的假判据，害得 12 个系列批量跑连续
挂了好几轮。记下来免得重犯：

**① 面板开没开：不能只看「筛选」两个字在不在。**

真机上「筛选」出现在两个位置、字号差一倍：

| 状态 | 位置 | 字号 |
|---|---|---|
| 面板关 | y=200 / x=244（按钮上的小字） | 16×15 |
| 面板开 | y=237 / x=410（面板标题） | 30×31 |

所以判据是**裁剪区 y228-285 / x400-500** 里有没有「筛选」——位置和字号
一起框住了，按钮上那个小字框不进来。

两个附加坑：

- **裁剪高度必须覆盖到 y≥270**。标题字高 31px、从 237 起，早期裁
  225-255 只盖到 255，字被切掉，OCR 无论开关都返回空 → 判据永远 False。
- **必须放大 2x 再 OCR，且不能要求「筛选」是同一个词**。WinRT 在这个
  100×57 的小裁剪里返回的是**单字** `['筛','选']`，不是合成词。早期写
  `any("筛选" in w["text"])` 永远匹配不上，面板明明开着也报 False。现在
  拼串后要求「筛」和「选」都出现，不依赖顺序（两字 y 可能差 1px，按
  (y,x) 排序会拼成「选筛」）。

**② 浮层开没开：不能用「探针区有没有字」。**

实测浮层左边框是 x=566 一条竖线：展开时 y340-660 内 **320/320 个像素
亮于 70**（均值 ~108），收起时同一位置**最大亮度 61、亮像素 0**。二值
差别，不受滚动位置影响。

探针区判据的两个死法：

- 面板关着时探针区里是皮肤列表的文字，OCR 读到就误判「已展开」；
- 浮层滚到第 3 屏时首项在 y=395，正好卡在探针区 y355-400 的下边界被
  切掉，误判「没展开」——「造物纪元」就是这么挂的。

**③ `_season_items` 在浮层收起时必须返回空。**

裁剪区 x555-765 / y340-700 在浮层收起后盖着的是**面板里的复选框文字**
（「传说品阶」「步枪」「精准射手」），OCR 照样读得出来。早期没这个
判断，重试路径把面板文字当成了下拉选项，报出
「找不到造物纪元（见过的：[...传说品, 步枪, 精准射手]）」——那些根本
不是下拉里的东西。加上 `if not _dropdown_open_img(img): return []` 之后
才干净。

#### 点完校验：下拉框也要 2x 放大

`_season_applied` 读收起态下拉框（y300-370 / x540-800）**必须放大 2x**。
15px 灰字在 1x 下整串读不出来：实测点 y=526 明明选中了「造物纪元」，
1x 裁剪返回空、2x 才读出「造物纪元」，于是被判「读不到 → 未确认」，
白试了 12 个偏移。这和 `_season_items` 是同一个坑。

#### 重试前必须重新展开浮层

`_click_season_item` 失败后浮层通常是收起状态。这时滚轮打在面板上没有
任何效果，而 `_season_items` 会判空返回 `[]` —— 白滚一轮，还把状态搞乱。
重试路径固定成「先点下拉框把浮层展开（每次验证，最多 4 次），再重扫」。

#### 复位时的 unknown 陷阱

从筛选面板连按两次 ESC 会进到一个认不出的画面（`unknown`），继续按就卡死。
`recover()` 改成：**unknown 连续出现两次就按 F4 重进市场** —— F4 只开不关，
已经在市场里时按它无副作用。

另外**面板开着时 ESC 只关一层**（先浮层、再面板），`where()` 在面板刚

##### 有些格子的字 OCR 永远读不出来 → 改用字形模板匹配（2026-10-21）

以下格子的文字只有 14px 高（实测包围盒高 13-14px，灰度峰值 192、背景 18），
`fx=1..6` 全部读不出：

|---|---|
| 稀有度「极品」「优品」 | 全空（「优品」fx=6 才勉强出） |
| 成色 S / A / B / C | 全空（单字母太小） |
| 材质「其他」 | fx=1 空，fx=2 才出 |
| 颜色「青色」 | 偶尔漏读 |

**原来的做法是查 `ONS_GRID` 表按位置反推**，但它依赖滚动位置推断（区块归属
靠竖直空隙切组 + 固定顺序），推断一错名字就错、而且没有任何信号。

现在改用**字形模板匹配**（`core/glyphs.py`）：

```
文字左边缘 = 方框中心 x + 25      垂直居中于方框中心 y，字高 14px
模板窗口   = (cx+24, cy-9) 起，80x18（比最长选项「镭射贵金属」71px 略宽）
```

匹配用 `TM_CCOEFF_NORMED`，在窗口四周留 4px 搜索余量。判据两条：
**分数 ≥ 0.88 且最佳与次优差 ≥ 0.10**，否则返回 `None`，交给下一通道。

阈值是量出来的：

| 情形 | 分数 |
|---|---|
| 同一选项在不同滚动位置 | 1.000 |
| 勾选态（勾选只改方框填充，不改文字） | 0.978 |
| 没有模板的格子（噪声最高分） | 0.63 |
| 最易混的一对（S vs B） | 0.873 |

所以 `ons_options()` 现在是**三通道**，按可靠性排序：

1. **字形模板匹配** → 有模板且分数够就用（像素证据）
2. **OCR** → 没有模板的选项（颜色区）靠它
3. **`ONS_GRID` 查表** → 最后兜底

字形排在 OCR 前面，是因为这几处小字 OCR 经常全空，偶尔出字也可能把
「极品」读成「优品」；而字形匹配是像素级比对。

返回项里 `src` 记录名字来自哪条通道（`glyph`/`ocr`/`grid`），`ocr` 和
`table` 是另外两条通道各自的结果 —— 三者不一致时说明有一路跑偏了，
这是排查「位置推断出错」的唯一信号。三条都对不上时该行**跳过**，不猜。

**真机验证（2026-10-21，`scratch/glyphreal.py`，4/4 通过）**：

```

滚 3 格后 20 项 材料+颜色全部 1.000，两屏共有格子名字 0 处不一致

```

**模板从哪来**：`core/assets/glyphs/<选项名>.png`，从真机截图切出的固定窗口，
跟着代码走、随 exe 打包（`sjz.spec` 的 datas）。注意和 `templates/` 的区别：
后者是用户自己框选的购买按钮模板，运行时生成、gitignore 掉；这里是游戏字体

所以 `ons_check(name, want=False)` 在「点完状态没变」且「该区块只剩这一项」

「最后一项」问题，直接报错更安全，不静默改掉筛选条件。

面板滚动后标题会滚出屏幕（实测滚 4 格后「材质」标题就不见了），
所以不能靠标题定位区块。真正稳的信号是**方框之间的竖直空隙**：

| 间距 | 值 |
|---|---|
| 区块内行距 | 56px |
| 成色最后一行 → 材质首行 | 118px |
| 稀有度 → 成色 | 175px |
| 材质 → 颜色 | 174px |

取阈值 **100px** 切分（介于 56 和 118 之间）。切出组后按固定顺序
`rarity → condition → material → color → more` 贴名字，标题锚点只用来
校正起始位置。

##### 三类会被误检成「方框」的东西

1. **面板标题「筛选」的「筛」字** —— y≈69，排除 `cy < 200`
2. **价格框里的金币图标** —— y≈170，同样靠 `cy < 200` 排除
3. **「〔可选至多2种〕」的「〔」括号** —— 26×20，比真选项小，排除 `w<24 or h<24`

另外每个真框会被边缘检测**检出两次**（29×29 外框 + 23×23 内框，中心
只差 3px）。不去重会让每个选项出现两次，其中一个状态还是错的。去重
规则：中心 <12px 合并，**保留面积大的那个**。

##### 面板可以滚动，坐标必须现读

面板内容超过一屏，滚 4 格后材质从 y745 移到 y219（差 526px）。所以
`ons_options()` **每次现抓屏、现做边缘检测、现 OCR**，不用固定坐标表。

方法：

- `Navigator.ons_options(scroll_top=True)` → `[{name, raw, box_pt, text_pt, on, block, row, col}]`
- `Navigator.ons_check(name, want=True)` → 按名字勾/取消，读状态确认
- `Navigator.ons_checks(names)` → 批量，超过 2 个直接 `NavError`
- `Navigator.ons_find(name)` → 整个面板里找（自动滚动），返回该项或 None
- `Navigator.ons_scroll_top()` / `ons_scroll_bottom()` → 滚到顶/底
- `Navigator.ons_ensure_block(block)` → 滚到指定区块，返回 bool

##### 滚动封装：为什么必须有

`ons_options()` **默认 `scroll_top=True`，先滚到顶再读**。这不是可选项 ——
区块名字靠「竖直空隙切组 + 固定顺序推断」，某个区块完全滚出屏幕时顺序
就推错了（实测滚 4 格后材质被当成 condition，成色 S/A/B/C 全丢）。
滚到顶部后第一个可见区块一定是稀有度，推断才唯一。

`ons_check()` 走 `ons_find()` 边滚边找，因为面板比一屏长：顶部只见
14 项，全量 23 项，「经典款」「彩绘款」在底部。只读一屏就报
「面板上没有这个选项」是错的。

**踩过的两个坑**：

1. 循环里用 `ons_options()`（默认滚回顶部）会把 `_ons_wheel(-3)` 的进度
   立刻抹掉，永远滚不下去，`ons_ensure_block` 恒返回 False。循环内必须
   传 `scroll_top=False`。
2. 单元测试里如果不对 `_ons_wheel` 打桩，测试会真的调 `ctypes` 移动鼠标、
   滚动游戏窗口 —— 测试从 11s 涨到 79s，而且真的会滚到游戏画面上。
   测试只桩 `_ons_wheel` 这一层，`ons_find` / `ons_ensure_block` 的循环
   逻辑仍被覆盖。

滚轮**必须用真实鼠标事件**（`SetCursorPos` + `mouse_event`），
`core.input.Mouse.wheel` 的 `PostMessage` 对游戏无效 —— 和价格输入框
同一类坑。

到底判定用「滚动后可见项签名有没有变」，不数滚动格数 —— 面板高度随
内容变化，数格数不可靠。

已接进 `engine._apply_price_filter()`（现已改名职责为「设筛选条件」）：
任务配了 `materials` / `colors` / `categories` 就在同一次开面板里一起勾上，
再点「确定」。顺序 `filter → price → checks → confirm`。

### 4.13 第三种触发模式：盯倒计时（2026-10-21）

用户原话：「不要管公示期，我现在想让你盯好剩余时间」。前两种模式（vanish /
appear）都要求按钮在开卖瞬间有可辨识的像素变化；有些商品从「不可点」到
「可点」长得一模一样，只能靠时间。

**先分清两种倒计时 —— 归零后结果完全相反（2026-10-21 真机发现）**

交易行里有两行长得像、含义相反的时间，一开始差点对着错的那行掐点：

| 位置 | 文字 | 归零时 |
|---|---|---|
| 在售页 | `剩余：2分31秒` | 商品**下架**，按钮变灰，显示「已过期」 |
| 公示期（筛选「只显示公示期」） | `2分31秒后解锁购买` | 解除限制，**可以买了** |

实测过程：在「在售」页挑了一件剩 207 秒的，生产循环一路跟到归零、开点提前
93ms，结果 1.6 秒后详情面板变成「已过期」、价格按钮从绿框高亮（亮度 37、
绿偏 +12）变成灰底（亮度 49.5、绿偏 +5）。同一件、同一个编号，没换过 ——
它从头到尾都是「上架剩余时间」，掐它没有任何意义。

切成「只显示公示期」之后，文字变成 `0分58秒后解锁购买`，解锁那一刻同一行
直接换成 `剩余：2天23小时`，按钮进入可点状态。**这才是抢购要盯的那一行。**

所以 `countdown.kind()` 把两者分开：读到 `剩余：…` 时引擎当场报错中止，并
提示把筛选切成「只显示公示期」，而不是闷头空点一场。

**筛选由程序自己切（`Navigator.pub_filter`）**

倒计时模式启动时会先 `nav.pub_filter("只显示公示期")`，不让用户记着手动切。
这个下拉有三个坑，全是真机踩出来的：

| 坑 | 现象 | 做法 |
|---|---|---|
| 14px 小字原尺寸读不出 | 整行被 WinRT 跳过，读到 0 行 | 裁剪后 `_upscale(2x)` 再 OCR |
| 每个汉字是独立词 | 拿「只」去比「只显示公示期」永远不中 | `_phrases(gap=60)` 归行拼整句 |
| 末尾「期」读成「恚」 | `不限公示恚`、`不显示公示` | 只用前两字当键（不限/只显/不显） |
| 菜单框含按钮那行 | 读到 4 行，第一行是按钮当前值 | 框从 y=235 起，避开按钮 |

真机验证（`scratch/navpub.py`，跑的是生产 `Navigator`）：

    只显示公示期 -> 不限公示期    点 (424,243)，顶部读回 '不限公示期'
      列表：'剩余：0分35秒' [remain]  ← 正是会误导的那种
    不限公示期 -> 只显示公示期    点 (440,290)，顶部读回 '只显示公示期'
      列表：'0分12秒后解锁购买' [unlock]

切完记得刷新列表（刷新图标中心 `(1377,195)`，模板匹配分数 1.000）—— 只改
筛选不会让已加载的卡片重新排序，旧卡片的状态还是旧的。

**为什么不能等「0分0秒」**

倒计时一秒一跳。显示「0分0秒」的那一整秒里，真实剩余可能是 0.99 秒，也可能是
0.01 秒 —— 拿它当触发时钟，最坏晚整整一秒。抢购窗口按毫秒算，这一秒足够被
别人买走。

真正能用的信息是**跳秒的时刻**：显示从 7 变 6 的那一瞬间，剩余时间是一个确定
的整数秒。所以每看到一次「值变成 S」，就得到一个归零时刻的估计：

    归零时刻 ≈ 观测到 S 的时刻 + S

取所有观测里最小的那个，误差收敛到一次轮询间隔（实测 10~20ms）。倒计时剩得
越少估得越准，正好是发力的时刻。

**floor 还是 ceil —— 2026-10-21 真机标定，答案是 floor**

单看一张截图分不清「显示 6」意味着剩余在 [6,7) 还是 (5,6]。两种可能：

| 模型 | 跳进 S 时真实剩余 | 归零时刻 |
|---|---|---|
| ceil | 正好 S | t + S |
| floor | S + 1 | t + S + 1 |

`scratch/calib_live.py` 在真机上跟了一整轮：178Hz 采样，采满 **81 次跳秒**，
从「剩余 1分20秒」一直跟到 0 之后再停 3 秒。结果：

| 观测 | 值 |
|---|---|
| 跳秒间隔 | min 0.996s / max 1.005s / avg 0.996s（没有漏秒） |
| 显示从 1 跳到 0 | 79.655s |
| 显示从 2 跳到 1 | 78.659s |
| **购买按钮变成可点** | **80.653s** |

两条互相独立的证据都指向 floor：

1. 显示跳到 0 之后 **0.999 秒**按钮才变；跳到 1 之后 2.000 秒才是那一刻。
2. 起始显示 80：ceil 会把归零放在 (79,80]，floor 放在 [80,81]。实测 80.653
   —— 只有 floor 装得下。

所以 `DISPLAY_TRUNC_S = 1.0`。**显示「0分0秒」的那一整秒里东西还没开卖**，
等它出现「0」再点，正好晚一秒。

回放验证：把记录下来的 81 组「时刻 + 显示值」喂给生产代码的 `Clock`，算出
归零在 **80.654s**，实测按钮变化在 **80.653s** —— 误差 1ms。旧模型（t+S）
会落在 79.654s，早 999ms。

**公示期那行也单独标了一次（`scratch/ucal.py`）**

上面那次是在售页的「剩余」。真正要抢的是公示期的「后解锁购买」，得单独验：

| 观测 | 值 |
|---|---|
| 起始显示 | `0分58秒后解锁购买` |
| 采样 | 60 次跳秒，间隔 min 0.015 / max 1.013 / avg 0.871 |
| **实测解锁时刻**（文字翻成「剩余：2天23小时」） | **52.374s** |
| floor 模型（t+S+1） | 52.362s → 误差 **-12ms** |
| ceil 模型（t+S） | 51.362s → 误差 -1012ms |

两种倒计时用同一个 `DISPLAY_TRUNC_S = 1.0`，都落在 floor 上。

**开点比归零早 5 秒**（2026-10-21 用户实测改，早期是 100ms）

`Clock.due(t, lead=FIRE_LEAD_S)`，`FIRE_LEAD_S=5.0`：用户实测公示期按钮在
归零前 5 秒就已经能点 —— 等归零是跟所有人同一刻抢，早 5 秒反而稳。相位估计
在 floor 模型下最多偏晚 1 秒，实际开点落在归零前 4~5.5 秒。早了只是空点几下
（按钮还没亮，点了没反应，`_fire_and_confirm` 会一直点到弹窗出现），晚了就是
被别人买走。

（历史数据：100ms 提前量那轮，在售页实测开点在 80.554s、比按钮变亮早
99ms；公示期生产循环复验返回时刻误差 -99ms。改 5 秒是真机实测按钮提前可点
之后用户定的，测试见 `tests/test_countdown.py` 的 5 秒提前量用例。）

公示期生产循环复验（`scratch/watch3_admin.py`，真机、提权、跑的是
`Engine._watch_countdown` 本体）：46 秒那件，最后一次 tick 预测归零
41.476s，实际返回 **41.378s**（差 -99ms），返回瞬间倒计时区仍是
`0分0秒后解锁购买` —— 正好卡在解锁前一刻，接着由 `_fire_and_confirm`
以 50Hz 连点到确认弹窗出现。

**真机 OCR 实测**

用户截图（201×61，游戏原字体）跑真机 WinRT OCR：

| 放大 | OCR 原文 | `parse` |
|---|---|---|
| fx=1 | `0 剩余 ： 0 分 6 秒` | 6 |
| fx=2 | `0 剩余 ： 0 分 6 秒` | 6 |
| fx=3 | `0 剩余 ． 0 分 6 秒` | 6 |

- 两个兜底：倒计时停更 2.5 秒 → `Aborted`；**6 秒一次都没读出秒数 → `Aborted`**

### 4.15 前端重做：三步向导 + 每目标条件 + 限量/预算（2026-10-22）

参考竞品「Axon·skin」的配置界面（用户提供截图）重做「任务队列」页。
值得抄的不是配色，是**结构**：

| 竞品的做法 | 我们的旧界面 | 现在 |
|---|---|---|
| 顶部三步向导：选目标 → 定条件 → 启动监控 | 一页平铺：队列 + 方式 + 单条 + 批量四块 | 三步向导，一次只做一件事 |
| 每个目标是一张卡，条件跟着目标走 | 只有一个全局价格区间，所有任务共用 | 每个目标单独的价格/品质/成色/磨损/限量/预算 |
| 右侧常驻「方案汇总」+ 预算上限 + 停止条件 | 没有汇总，也没有「抢几件」的概念 | 第 3 步先核对汇总再启动 |
| 本轮限量（抢够 2 件跳下一个目标） | 抢到一件就 DONE | `quota`，抢够才 DONE |
| 预算上限（花超就停） | 无 | `budget`，超预算的整行不点 |
| 目标先配置、最后统一点「启动」 | 边填边进队列，半成品也在队列里 | 目标存本地草稿（`localStorage`），点启动才排队 |

#### 后端补的两个字段

`Scheduler.add(..., quota=1, budget=0)` → 任务里存 `quota`（本轮限量，≥1）
和 `budget`（预算上限，0 = 不限）。`/api/tasks/add`、`/api/tasks/add_many` 透传。

`Engine._execute_list` 里的用法：

- 抢到一件：`bought += 1; spent += row["price"]`，`bought >= quota` 才 DONE，
  否则清空 `tried`、刷新列表、继续抢（限量 2 件就要真的抢两件）。
- 预算：挑货前先把 `spent + price > budget` 的行整行剔掉。不剔的话「买不起」
  会被当成「没抢到」，白点一次购买，还可能真成交。剔完没有候选 → 收尾。

#### 前端结构

```
#wSteps        三步条（data-step=1/2/3，.on 当前，.done 已过）
.wstep         每步一个容器，只有 .on 的那个显示
#wCards        目标卡片（点选、× 删除、副标题写条件）
#wPick         第 2 步的目标切换（分段按钮，多了自动换行）
#eMin/#eMax/#eCraft/#eWear/#eWearMax/#eQuota/#eBudget   每目标条件
#pMode/#pAt/#pGap                                       全局：方式/开卖时间/间隔
#wSum/#wReview/#wStart                                  第 3 步：汇总/复核/启动
```

草稿键 `sjz_plan_v1`（`{mode, targets[]}`）：加/删目标、改任何条件都落盘，
刷新不丢。点「启动监控」才逐条 `POST /api/tasks/add`。

校验（都在 `#wNext2` 和 `#wStart`）：在售列表模式下每个目标必须有价格上限
（没上限 = 全档位乱抢）；下限不许 ≥ 上限。

#### 没做的（明确记下来）

- 竞品的「购买延迟 840ms / 动态微调」没接：我们的开点提前量是常量
  `FIRE_LEAD_S=5.0`（2026-10-21 用户实测按钮提前 5 秒可点后定的），
  没做成可调。
- 竞品的「按稀有度停止条件（传说 2 / 紫 5 / 蓝 8）」没做：我们的货行只识别
  做工（极品/优品）和成色（S/A/B/C），没有可靠的稀有度字段，硬做只能靠猜。

### 4.16 启动前检查：五项全过才允许启动（2026-10-22）

参考竞品第 3 步的「启动前检查」：不是提醒你去检查，而是**把启动按钮卡住**。
理由是抢购失败大多不是引擎写错，是开工前环境不对 —— 而这些错现在都要等到
「点了启动、跑一轮、看日志」才暴露，那时已经错过一批货。

| 检查项 | 判据 | 不过时给的动作 |
|---|---|---|
| 游戏窗口 | `Screen.size == (1920, 1080)` | 去运行页：改成窗口化 1920×1080 |
| OCR 识别 | `ocr.available()` | 去运行页：装中文 OCR 语言包 |
| 时间校准 | `abs(offset) <= 0.2s` | 去运行页：重新校时 |
| 按钮模板 | 列表模式要 `confirm` + `list` 区域；详情模式要 `buy` + `confirm` | 去框选页 |
| 游戏页面 | 列表模式必须 `onsale`；`unknown` 一律不过 | 去框选页：切到交易行 |

`core/preflight.py` 分两层：`evaluate(facts, mode)` 是纯函数（测试打这里），
`collect(cfg, mode)` 才真的抓屏 / 问 OCR / 读校时 / 认页面（约 1 秒）。
端点 `POST /api/preflight {mode}`，进第 3 步和点「重新检查」时调。

前端：`#ckList` 一行一项（✓ / ⚠ + 标题 + 说明 + 「去处理」），
`#ckCount` 显示「4/5 通过」，`#ckNote` 红字「还有 N 项未通过，启动按钮已禁用」，
`setStartEnabled(ckOk)` 控制 `#wStart`；`#wStart` 处理器里再挡一道 `if (!ckOk)`。

真机实测（2026-10-22，游戏在售页，窗口化 1920×1080）：


### 4.19 桌面化：start.bat 直接开 pywebview 窗口 + 两个热键（2026-10-22）

**入口**：`start.bat` 不再 `uv run python run.py`（开浏览器），改成
`.venv\Scripts\pythonw.exe desktop.py`（`start ""` 起，bat 立刻退出、不留黑框）。
优先级：项目自带 `.venv` → `uv` → 系统 `python`。这台机器上根本没装 uv，
所以原来那个 bat 双击只会打印「uv not found」—— 一直没被发现，因为开发时都手敲 `run.py`。

三个坑：

| 坑 | 现象 | 修法 |
|---|---|---|
| `.bat` 用 LF 换行 | cmd 把 UTF-8 中文注释的字节当命令执行，报「不是内部或外部命令」，然后照样往下跑 | 写成 **CRLF + GBK**；中文注释才不会被拆碎 |
| 同步调用 `pythonw.exe` | bat 一直挂着，黑窗口不消失 | `start "" ".venv\Scripts\pythonw.exe" desktop.py` |
| pythonw 无控制台 | 启动失败 = 双击没反应，什么都看不到 | `desktop.log` 记全过程 + 末尾 `MessageBoxW` 弹错误 |

`desktop.py` 里 webview 改成可选：`import webview` 失败、或 `webview.start()` 立刻返回
（WebView2 缺失），退化成本机 Edge/Chrome 的 `--app` 独立窗口（无地址栏无标签）；
连可用浏览器都找不到就弹错误并退出，**不再退回浏览器标签页，也不留后台僵尸进程**。

**热键两个**：`config.hotkey = {enabled, spec, start_enabled, start_spec}`，
停止默认 F8、开抢默认 F7，各自一条 `RegisterHotKey` 消息循环，互不影响。
`_hotkey_toggle()` 的语义：在跑 → 停；没跑 → 过启动前检查 → `start()`。
**热键跳过的是界面，不是检查**：五项不过就不开，把不过的那几项写进调度器日志
（`Scheduler.note()`），否则按了没反应又查不出原因。队列空 / 全停用也不开。

顺带修掉一个真 bug：热键原来只在 `POST /api/hotkey` 时注册，**重启后一个都不生效**
（`/api/hotkey` 显示「未启动」）。现在 `serve()` 起来就注册，桌面版日志里能看到两行。

真机验证（2026-10-22）：
- `start.bat` 双击 → 窗口出现（PrintWindow 抓图，1164×761 全渲染），bat 立即返回
- `/api/hotkey` → `F7 已就绪` / `F8 已就绪`
- 抢前台后合成一次 F7 → 调度器日志出现「热键开抢：队列是空的（或全部停用）」
- 把键改成 `XX99` → 界面老实报「认不出热键「XX99」」，改回 F7 恢复

### 4.20 记录页：每一次尝试都留痕（2026-10-22）

竞品「记录」页给的是：9 张统计卡 + 一张 6 列表格 + 右侧详情（含成交截图）。
我们抄的是**能算准的那部分**：

| 竞品指标 | 我们 | 说明 |
|---|---|---|
| 抢购成功 / 购买成功 / 假购买 | 抢到（件） | 只有「成交」一种结果，没有假买/排队 |
| 进池率 = 排队成功 / 总样本 | 命中率 = 抢到 / 尝试 | 分母是**每一次尝试**，不是成功次数 |
| 中位延迟 830ms | 耗时（单次） | 我们记的是这一枪的实际耗时，不是延迟 |
| 摇奖结果 / 服务器反馈 | ❌ | 游戏没有这个数据源 |
| 记录详情 + 成交截图 | 看图 | `/shots/<文件名>`，中文名 percent-encoded |

数据：`data/records.jsonl`，一行一次尝试。为什么是 JSONL 不是 JSON 数组：
抢购边抢边写，追加不用重写整个文件，进程被强杀最多坏最后一行，读的时候跳过。

字段：`ts / t / name / price / result / elapsed / shot / mode / quota`，
`result` 五码：`hit / miss / no_money / over_budget / aborted`。

接线在 `Engine._record()`：`_fire_and_confirm` 成功写 `hit`、没等到弹窗写 `miss`，
每次尝试都写一条。**只有 hit 才存截图** —— 开关叫「成交后存截图」，没抢到也存就是骗人。

三个坑：

1. **统计口径**：命中率一开始写成 `hits / hits`，永远 100%。测试用
   「2 命中 / 3 尝试 → 66.7%」把它钉住。
2. **中文文件名 404**：商品名直接进了文件名，URL 里是 percent-encoded 的，
   `_shot_file` 不 `unquote` 就永远 404 —— 浏览器只显示一张破图，服务端一声不吭。
3. **穿越守卫测了个寂寞**：只用不存在的路径（`/shots/../config.json`）测 404，
   守卫删掉也照样 404。必须拿一个**真实存在**的 `.jpg`（`/shots/../../web/assets/df-bg.jpg`）
   去撞，才能证明守卫真的在挡。

真机：写入 5 条样例 → 统计卡 `3 件 / ¥2,718 / 5 次 / 60%` 与表格一致；
`/shots/<中文名>` 返回 `200 image/jpeg 182756B`；清空后 `stats` 归零，截图文件不动。

### 6.1 nav 模块的拆分（按页面职责）

`core/nav.py` 原来把「坐标表 + 通用导航 + 两个页面的面板驱动」挤在一个
2000+ 行的文件里，改一处要通读全文。现按职责拆成四个模块，依赖单向、
没有环：

| 模块 | 职责 |
|---|---|
| `core/nav_coords.py` | 坐标标定表 + `FORBIDDEN` 禁用点表 + `NavError` + `_scaled` 换算 |
| `core/nav_col.py` | 典藏外观页（`COL_*`）：赛季下拉、拥有/品阶/枪种复选框、皮肤卡片、购买 |
| `core/nav_ons.py` | 在售页（`ONS_*`）：价格区间、稀有度/成色/材质/颜色筛选、公示期、翻页 |
| `core/nav.py` | `NavBase`（通用导航 + 点击护栏）+ 页面识别 `classify` / `tab_from_pixels` + `Navigator` 组装 |

`Navigator` 由 mixin 组合而成：`Navigator(NavOnsPanel, NavColPanel, NavBase)`。
两个面板都是**纯方法 mixin，不定义 `__init__`**，运行时 `self` 就是
`Navigator`，所以跨面板调用（`recover()` 会问 `self._panel_open()` 和
`self._ons_filter_open()`）照旧成立。

`from .nav import NavError, Navigator` 这条 import 路径保持可用
（`NavError` 从 `nav_coords` 转出），`core/engine.py` 不受影响。


## 4.21 版式重做：照竞品那三页的骨架

用户给了竞品「Axon·skin」的运行台 / 目标库 / 记录三页截图，要求「直接抄图片做前端 UI」。
抄的是**骨架**，不是每个数字：

| 竞品 | 我们 | 说明 |
|---|---|---|
| 顶栏：品牌 + 六标签 + 状态 + 运行时长 + 启停 + 窗口钮 | 同结构，五个标签（抢购/目标库/记录/识别/设置） | 我们没做「分析/日记」，那两页后端没有数据源，摆上去就是空壳 |
| 三栏：当前任务 / 队列 / 会话统计+日志 | 左「当前任务+启动前检查」/ 中「队列+加目标」/ 右「关键动作+日志」 | 会话统计并进左栏的「本轮抢到 / 本轮花费」 |
| 底部状态条：游戏 / OCR / NTP / 版本 | 同，外加本地时钟与分辨率 | 分辨率是硬要求（所有坐标按 1920×1080 标的），所以它就是「游戏就绪」的判据 |
| 目标库：左赛季栏 + 卡片网格 + `+` | 同 | 卡片里的「图」我们没有素材，用枪型号大字占位，不伪造皮肤图 |
| 记录页：统计卡 + 表格 + 右侧详情 | 同 | 详情栏给时间/结果/价格/耗时/模式 + 截图；没截图就写「只有抢到才存」 |

**三个坑**：

1. **`#tabs` 原本是左导航的竖排容器**。搬进顶栏后不覆盖 `flex-direction: column`，
   六个标签会折成两行把顶栏顶高。必须写 `#tabs.tabs { flex-direction: row }`
   —— 用 `.tabs` 加权重，比改 id 安全（JS 的切换逻辑靠 id）。
2. **重复 id 不会报错，只会让左边那块永远不动**。搬家时「实时状态」和「启动前检查」
   各出现两份，`$('#stState')` 只认第一个 —— 左边新卡永远显示「没在跑」。
   搬完必须扫一遍 `id=` 查重（现在是 0 个重复）。
3. **`.dash` 用 `height: calc(100vh - 顶栏 - 底栏 - 边距)` 撑满**，配合
   `.dcol.c2 > .card { flex: 1 }`，队列卡才会吃掉剩余高度；只写 `align-items: start`
   会三栏各自缩成一团，下半屏全是黑的。

**没抄的**：假购买、排队已满、进池率、摇奖结果、按稀有度停止 —— 这些我们没有数据源，
做成开关就是骗人。能算准的（抢到件数、花费、尝试次数、命中率、单次耗时）才做。

## 4.22 设置拆四块 + 记录分会话 + 分析页

照竞品设置页（常规 / 热键 / 识别与校时 / 抢购高级）与「分析」页的骨架继续抄。

**设置页**：左列 `.setnav` 四个按钮，右边 `.setpane` 四块，只切 `display`。
原来五个 `.sec` 平铺，热键和对时间混在一起，找一个开关要往下滚。四个数字
（相似度下限 / 到点宽限 / 触发超时 / 一页最多试几条）走 `POST /api/config`，
白名单**必须**同时加 `arm_grace_s`、`list_max_tries` —— 漏一个就是「点保存、
提示已保存、其实没存」，下次开抢才发现还是老参数（已有测试钉住）。

`trigger_mode` 在向导里也有一份，两处控件必须一起变（`paintTrig()` 同时刷
`#advTrig` 和 `#trigSeg`），否则同一页面上两个控件互相打脸。

**记录页**：按时间戳分段，两次尝试隔超过 10 分钟就是另一场，段头写
「起–止 · N 次尝试 · 抢到 M · ¥X · 中位 Y ms」，左边竖条绿/黄/红。
记录里没有场次号，这个边界是**推出来的**，所以文案写「会话」不写「任务」。

**分析页**：只做能算准的 —— 成功率、尝试次数、平均/中位耗时（P10/P90）、
耗时分布直方图（动态分箱：我们耗时集中在 0.8s，固定刻度会全挤一格）、
结果构成（我们自己的五种结果）、时段表现（4 小时一段）。
竞品的「进池率 / 假购买 / 排队已满 / 人数过多 / 支付失败 / 摇奖」全都没做 ——
这些要从点击回执里分，我们没有那个信号，画上去就是编数字。测试里直接断言
这些词不许出现在分析页代码里。


## 4.23 列表扫描：先定位商品，再识别商品

旧路子是「整屏 OCR + 按词距聚类成行」。它错在把**版式**当成了**文字间距**：
一张卡里「名字」到「价格」的水平距离，比两张卡之间的缝隙还大，聚类时价格会被
并进上一张卡，型号里的数字（QBZ95、M250）会被当成价格。真机上表现为「价格忽大
忽小、偶尔整行串位」。

新管线（`core/cards.py` + `core/market.py::scan`）：

```
整屏截图 → 裁出列表区域 → OpenCV 找卡片矩形 → 每卡切 名称/底行/图标
        → 各自放大 3 倍 → WinRT 只认这三小块 → 价格只取底行
```

`market.Scanner` 在这一层上加帧间缓存：逐卡比较相邻两帧，只有变了的那张卡重新
认字。列表模式 20 次/秒，一屏六张卡通常只有一张在变。

### 踩过的坑（每条都在 `tests/test_cards.py` 里钉住了）

| 现象 | 根因 | 解法 |
|---|---|---|
| 六种定位法全失败：Canny 峰、亮度阈值+连通域、行/列亮度凹陷、blur 取中值带、std 图、kmeans | 卡片是**半透明面板浮在场景上**，底部还有渐变背景，亮度和边缘都不构成「卡片边界」 | 找**够长的直线**（竖线跨 1 张卡高、横线跨整屏），竖线两两配 × 横线两两配 |
| 竖线检测不到中间那条分隔线 | 分隔线只跨一张卡高，占全图比例 ~17%，`frac=0.18` 正好把它筛掉 | 竖线 `frac=0.12`，横线保持 `0.25` |
| 最后一行永远读不出价格 | 行距按上一行间距推算，最后一行短二十来像素，正好切掉「极品 \| 成色 C 9,000」的下半截 | `locate_cards` 把最后一行补到画面底边 |
| 明明有字，OCR 返回空串 | WinRT 对**紧贴文字**切出来的一条（高 14px）返回空串 | 文字块上下各留 `PAD=8`；贴边时**整体平移**而不是裁掉边距（裁掉等于没留） |
| 2000x70 的价格行 OCR 空串 | 宽高比 28:1，引擎放弃 | `_pad_aspect` 用卡片底色补到 10:1 以内 |
| 价格读成 205002050 | 按 55% 硬切底行，成色文字长度一变就把价格切掉一半，两张卡的价格粘在一起 | 底行**整条一起认**，再从同一段文字里取成色和价格 |
| 25000 读成 25 | 金币图标被认成前导 0、逗号被当小数点 | 只留数字，位数 < 4 视为没认出来（宁可跳过也不拿 288 比 28888） |
| 缓存把旧价当新价用 | 整卡平均差会把「12,000 → 12,500」这种小改动稀释掉 | 改成 6x6 分块取**最大**块差 |

### 真机验证后改的三处（2026-10-22 夜，在售页实测）

| 现象 | 根因 | 解法 |
|---|---|---|
| 六张卡只认出 2~4 张，成色时有时无 | 同一张卡有**两种版式**：可买的卡「成色+价格在上、名称在下」，公示中的卡「名称在上、成色+价格在下」。按位置切死必然错一种 | 不再按位置切，改成**找出所有有字的横带**（枪的图案占卡片四成高，按高度筛掉），逐条 OCR 后按内容归类 |
| 价格被读成 41 | 成色带里没数字时退到「有数字的那条带」，名称里的 `M4A1` 变成 41 | 先定名称（最长带中文的那条），挑价格时**排除名称带** |
| 价格全是 None | 按「位数 < 4 就不可信」过滤，可真机上有 2 个三角币的挂单（用户确认） | 卡片路径不设位数下限，只去掉金币图标认出来的前导 0；`_scan_grid` 退路仍按 `_MIN_PRICE` 兜底 |
| 成色和价格挤在同一条带（`成色 S  05`） | 分带时它们本来就在同一行 | 成色带里出现数字就直接当价格，不再去别的带找 |

真机实测（在售页，1920×1080，列表区域 60,210,1340,730）：定位 6/6 张卡 15ms，
名称和成色 6/6 认对，价格 4/6（两位没认出来 → 该行按「读不出价」跳过，不会误买）；
`Scanner` 首帧 750ms、同一帧再扫 16ms。

### 接入点

`engine._execute_list` 用 `market.Scanner()`，列表刷新/翻页后调 `scanner.reset()`
（不清缓存会拿旧价去比新货）。测试里替换 `market.scan` 的假函数仍然接得上：
`Scanner` 在找不到卡片线时按原样调用模块级 `scan(img)`。

### 4.24 真机复测：坐标没变，拦路的是 UIPI（2026-10-23）

重构完 core/ 之后在真机上整套跑了一遍。结论分两半：

**坐标表仍然准确，一处没改。** 实测：

| 步 | 动作 | 变化率 | 页面判定 |
|---|---|---|---|
| 1 | 主界面按 F4 | 21.1% | `market` ✓ |
| 2 | 点「典藏外观」(323,55) | 13.0% | 左侧砖皮目录：MK4·疾光魅影 / AKM·群星 / KC17·造物纪元… |
| 3 | 选卡 | — | 卡片已是选中态 |
| 4 | 点「购买」(1700,885) | 58.3% | `onsale` ✓ |
| 5 | 切「只显示公示期」 | 10.3% | 列表变成公示期货 |
| 6 | 价格框输入 1000 → 读回 | — | **2050**（游戏抬到自己的最低价，只筛更窄 → 放行 ✓） |
| 7 | 典藏页筛选「品阶·普通」 | — | 复选框亮像素 0→356 ✓，列表切成普通品质砖皮 |

砖皮卡片的纵坐标也和代码一致：名字行 OCR 在 y=260/374/488…，「典藏」标签在
y=337/451/565…，卡片中心 (260+337)/2 = 298 = `SKIN_CARD_Y[0]` ✓。

**拦路的是 UIPI，不是坐标。** 游戏以**管理员**（High）运行、控制台以普通
权限（Medium）运行时，Windows 会把控制台发出去的鼠标键盘消息**全部拦掉，
而且一声不吭**：

| 机制 | 结果 |
|---|---|
| SetCursorPos + PostMessage 点击 | 无反应（画面只变 2~3%，是待机动画） |
| PostMessage 键盘（F4） | 无反应 |
| SendInput 点击 / 键盘 | 无反应 |
| mouse_event（旧 API） | 无反应 |
| SendMessage（同步） | 无反应 |

提权之后，**同一套代码**立刻全部生效（上面那张表就是提权后测的）。
关键判据：`GetTokenInformation(TokenIntegrityLevel)` 取到游戏是 `0x3000`
（High）、控制台是 `0x2000`（Medium）。

已做进产品：
- `core/input.py`：`process_integrity()` / `foreground_integrity()` / `elevate_self()`
- `core/preflight.py`：启动前检查多一项「程序权限」，低权限直接拦住并说怎么修
- `core/engine.py`：`_validate()` 同样先查权限 —— 权限不对就别开跑（会白跑一轮，
  还会被误判成「没抢到」）
- `desktop.py` / `run.py`：启动时发现游戏权限更高就弹 UAC、用管理员身份重开自己

**另一个坑**：顶栏「交易行」进的是**交易页**（购买/出售/交易记录 + 收藏/枪械/
装备/配件/弹药/收集品/消耗品/钥匙 分类），**不是**市场页。市场页只能按 F4 进
（大厅 → F4 → 曼德尔砖/典藏外观/典藏挂饰）。走错页时页面识别会判成 `hall`，
看起来像「代码不认页面」。

### 4.25 幽灵屏：抓屏抓到不再刷新的旧画面（2026-10-23）

症状：记录里冒出一笔「成交」，没有商品名、耗时上万秒（4 万多秒），
点开截图是**典藏外观的卡片列表**，而且那张图和 9 小时前的一张 **md5 完全
相同**。

原因：mss 的显示器列表里残留了一块**幽灵屏** —— 设备早拔掉或改过分辨率，
系统还没把它的条目清掉。`Screen(1)` 按下标取就取到了它，而幽灵屏**不再
刷新**：每帧都是同一张冻结画面。引擎于是把画面里的「跳过」当成成交弹窗，
凭空记了一笔「成交」。

修法：`core/screen.py` 选屏时**按主显示器的尺寸匹配**（`GetSystemMetrics`
问系统要），不再死按下标取。`tests/test_screen.py` 用一块假幽灵屏守住这条。

附带修的一条：在售页和详情页的**右侧详情面板长得一样**（都有「相似皮肤」
「编号」「淘汰计数」），区分两者靠的是在售页底部的「第 N 页」—— 那是 12px
的小字，整屏 1 倍 OCR 读不到，于是**在售页被判成 detail**，导航跟着走错。
现在 `nav._read_text` 会额外高倍读页码那一小块（540x60 放大 6 倍，几毫秒）。

### 4.27 品阶目录：每个赛季 × 四个品阶的全部皮肤（2026-10-23）

砖皮知识库原来只有每个赛季的**典藏**档砖皮。游戏里每个系列（赛季）都有
普通 / 稀有 / 史诗 / 传说 四个品阶的皮肤，典藏外观页的筛选面板就是按
「系列 + 品阶」过滤的 —— 要「找到某一砖」，就得知道它在哪个系列、哪一档。

#### 界面的真实结构（和旧标定不一样了）

| 元素 | 旧标定 | 真机（2026-10-23） |
|---|---|---|
| 皮肤列表 | 左侧一列小字卡片 | 左侧一列**大字卡片**，名字**被游戏截断**（「AK-12突…」） |
| 完整名字 | 列表里就有 | 在**标题栏**（屏幕中间 474..893 / 177..220，字号 28~31px） |
| 详情面板 | 右侧 x1330-1920 | 右侧只有「我的关注 / 典藏工坊」 |
| 「查看：未拥有」 | x=605 | **x=806**（605 落在两个框中间的空地上，点下去没反应） |
| 「品阶」四个框 | x=580/818/1058/1296 | 一样 ✓ |
| 「典藏外观·筛选」 | (275,206) | 一样 ✓ |

「未拥有」坐标错的后果很阴：那个筛选一直关不掉 → 列表里只剩**已拥有**的
那几件 → 采集出来每档只有 1~4 件，还以为「这档就这么点皮肤」。

#### 采集办法

11 个系列 × 4 个品阶 = 44 组，每组：选系列（赛季下拉）→ 只留一个品阶 →
**「已拥有」「未拥有」两个都勾**（只勾一个就只剩一半：实测 S1·普通
已拥有 1 件 + 未拥有 6 件，两个都勾 = 7 件）→ 确定 → 列表从顶往下滚 →
**逐张点开读标题栏的完整名字**。

两条数据源的分工：
- **武器型号**取左侧列表（「QBZ95．1突击步枪」认得准）
- **皮肤名**取标题栏（完整）
- 标题里的武器型号认得烂（→「OBZ．1」「0〔0171」），列表里的皮肤名被截断

洗完并进 `core/bricks.json` 的 `seasons[].tiers`，共 **181 件**。
清洗规则：分隔符统一成「·」；皮肤名按**相似度聚类**后取簇内多数写法
（「迷彩/迷采/迷未」是一个词）；系列名用知识库里的正式叫法纠正
（「檀劫铳影」→「疾光魅影」）；型号里被 OCR 吞掉的连字符补回来
（AK-12 / QBZ95-1 / SCAR-H / SMG-45）。

#### 用起来

```python
bricks.find_skin("AK-12突击步枪·水墨迷彩")
# → {'name': 'AK-12突击步枪·水墨迷彩', 'series': '棱镜攻势', 'tier': '普通', ...}

nav.select_skin(series="棱镜攻势", tier="普通", name="AK-12突击步枪·水墨迷彩")
# → 设筛选 → 滚列表 → 点中那一件，返回点击 y
```

真机验证 3/3 定位正确（标题读回相似度 1.00 / 1.00 / 0.77 —— 0.77 那件
是 OCR 把 Vector 认成了「V t 。 r」，但归一化后仍能定位到正确那张卡）。

比名字必须模糊：游戏用花体字，「彩」认成「采/未/米」、「白」认成「自」，
武器型号里的「-」认成「·」。所以比对前先归一化（去分隔符去空白）再比相似度。

#### 顺带修的坐标/行为

- `COL_NOT_OWNED` (605,414) → **(806,412)**（逐像素扫描：框的描边在 x=804~806，
  点 805 亮像素 0→183 勾上了）
- `COL_OWNED` (580,414) → (580,**412**)
- 新增 `nav.col_filter_states()`：把筛选面板当前状态**读出来核对**。
  勾选框是记忆的，「点了」不等于「游戏认了」—— 光看点击日志看不出来。
- 新增 `nav.set_tier(index)`：只留一个品阶（勾选框是累加的，不取消其它
  三档，列表里会混着别的档）。
- 新增 `nav.skin_title()` / `nav.skin_scroll()`。
- `skin_items()` 改成 2 倍放大再认，词组间距跟着放大倍数走
  （还是 14 的话「AK-12突击步枪·水墨」会被拆成两段）。

### 4.28 筛选面板有两种布局，坐标不能写死（2026-10-23）

典藏外观页的筛选面板，**布局会跟着后面的内容变**：

| 状态 | 面板形态 | 赛季下拉浮层 |
|---|---|---|
| 列表有货（筛得宽） | 贴边，浮层在 x555-765 / y340-700 | 选项行首项 y=379，间距 48 |
| 列表空（筛得只剩一两件） | **居中浮层**，整个面板占满屏 | 选项行整体下移 |

这一条把好几件事都坑了：

1. 「面板开着没」的判据（浮层左边框那条竖线 x=566）在居中布局下失效 →
   代码以为面板没开 → 去点「筛选」→ 那个按钮被浮层盖着 → 点不动 →
   整条链卡死（实测「下拉展不开」「不在可见范围」）。
2. 赛季选项的**点击热区**也偏了：贴边布局下热区在文字上方 16~28px，
   居中布局偏得更多。原来的偏移表够不着。
3. 顶栏「典藏外观」标签的绿框判据在浮层开着时读不到（面板盖住了顶栏）。

**改法**（都在 `core/nav_col.py`）：

- `nav._season_items_anywhere()`：按**文字**找选项，不再依赖固定裁剪区。
  裁剪只取「下拉那一竖列」（x540-830）—— 下拉按钮的位置两种布局都一样
  （x562-813），浮层是它下面展开的，所以这一列永远装着选项。整屏 2 倍 OCR
  要好几秒，不能那么干。
- `nav.col_filter_reset()`：把筛选复位成「全要」（四个品阶 + 七个枪种 + 已拥有/未拥有
  全勾）。列表满 → 面板贴边 → 坐标回到已知值。
- `nav.goto_collection()`：关掉开着的面板 → 判断是不是在市场页 → 不是就按 F4
  进市场 → 切典藏外观标签。定位某件砖前先走这一趟。
- `nav.set_gun(gun)` / `nav.set_tier(index)`：按名字设品阶/枪种，且**只留一档**
  （勾选框是累加的，不取消其它的，列表里会混着别的档 —— 实测「史诗」那档里
  还带着传说的货）。
- `nav.col_filter_states()`：把筛选状态**读出来核对**。勾选框是记忆的，
  「点了」不等于「游戏认了」——光看点击日志看不出来。

### 4.29 枪种：已用游戏筛选交叉核对（2026-10-23 补完）

目录里每件皮肤记着**赛季 / 品阶 / 型号 / 枪种**：

- 赛季、品阶：真机逐档采集（每个系列 × 每个品阶，滚遍列表逐张点开读标题），
  准。
- 型号、枪种：来自皮肤名本身（「M4A1突击步枪·棱镜攻势」→ 型号 M4A1、
  枪种 突击步枪 → 筛选面板那一档「步枪」），再用查资料的武器表
  （`core/weapons.py`，56 把枪）把 OCR 认错的型号对齐
  （`ASVa`→AS Val、`MISA4`→M16A4、`SCARH`→SCAR-H）。

**补完的那一遍**：在典藏外观页勾一个枪种、滚到底读全部卡片名 ——
游戏给的答案。系列选「全部赛季」、品阶全勾，只切枪种，七档各跑一遍，
把采到的名字和目录比对。结论：

- 目录和游戏**一致** 113 件；**对不上** 5 件，全是「手步枪·×」——
  游戏归「精准射手步枪」（SKS / Mini-14 / PSG-1 那类射手步枪），
  目录归「步枪」，**游戏是对的**。
- 目录里普通品阶（纯白涂装 / 雪地迷彩 / 蛇纹涂装这类）市场**根本不挂**，
  那是知识库不是挂单。

顺带修好的三个真 bug（都在这条路上踩出来的）：

1. **滚轮必须用真实鼠标事件**（`SetCursorPos` + `mouse_event`），
   发 `WM_MOUSEWHEEL` 消息游戏直接无视 —— 典藏外观的左侧列表滚 12 屏
   纹丝不动，每屏都是同样 6 件。
2. **滚动的方向符号**：上层「正数向下」、底层是 Windows 惯例「正数向上」，
   不翻符号就滚反方向，在列表顶部滚 12 屏全在原地。
3. **赛季名按单字归组**，不按整行认：OCR 会认错字（「群星」→「难星」、
   「疾光魅影」→「疾光赃影」）还会并错行。各赛季名的字互不重叠，
   按单字归属没有歧义；S1/S2 那种「棱镜攻势 / 棱镜攻势S2」靠完整度区分。

### 4.30 砖皮目录改成生成物（2026-10-24）

旧目录是照着游戏画面 OCR 采的，两个毛病：

- **型号名是 OCR 残骸** —— 175 件里 40 件的型号不在武器表内
  （`S步枪·纯白涂装`、`手步枪·花岗岩`、`U冲锋枪·蛇纹涂装`、`K4步枪·巨兽`）。
- **每块砖只收了 1/3 的皮肤** —— 一块砖是 1 传说 + 3 史诗 + 8 稀有 +
  10 普通，旧目录每赛季只有 16 件。

现在改成**从源数据生成**：`tools/bricks_source.csv`（三角洲曼德尔砖枪皮
数据库，243 条）→ `python tools/build_bricks.py` → `core/bricks.json`。

合并规则：

1. 条目、型号、赛季、品阶用源数据（和旧目录对上的 114 件里赛季/品阶
   零分歧）；
2. 枪种用源数据的细分枪种映射到游戏的筛选档；**游戏自己核过的以游戏
   为准**（SVD 那四件：源数据写「狙击步枪」，游戏归「精准射手步枪」）；
3. 旧目录里的赛季日期、赛季中文名、系列别名、系列备注、做工/磨损知识库
   沿用；
4. 识别层按**皮肤名**归组，不按系列 —— 「命运」和「王牌之剑」是两个皮肤名
   同属「命运王牌」系列，按系列归组的话「K416 突击步枪 命运」只剩型号命中，
   会被判成弱匹配。

**子系列 ≠ 砖名**：游戏「赛季下拉」里列的是砖名（棱镜攻势 / 美杜莎…），
子系列（水墨迷彩 / 青纹…）不在下拉里。目录现在同时给两个字段：
`series`（这一件自己的系列，给界面显示）和 `brick`（砖名，给定位用）。

### 4.31 典藏外观的两个定位坑（2026-10-24）

- **「交易 / 单据」两个二级页签**：皮肤列表和筛选面板都在「交易」下面；
  停在「单据」（购买记录）那一页时点「筛选」毫无反应 —— 那一页压根没有
  这个按钮。`col_filter()` 现在面板打不开就切回「交易」再试一次。
- **筛选生效后列表要重载**：点完「确定」列表要刷，期间读到的是旧的
  （甚至空的）。早前就因为这个报「列表里找不到「AKM突击步枪·群星」」
  （实测那一屏确实有货，只是还没刷出来）。`select_skin()` 现在等列表
  **内容变了**再找 —— 光等「非空」不够，旧列表也是非空的（实测换赛季
  后第一档读到的是上一季的五件）。

### 4.32 「点不动」的真正原因：游戏不在前台（2026-10-24）

早前一批「点击后状态不对」「点了「筛选」但面板没打开」的失败，一度以为是
筛选面板的**居中版式**（列表为空时游戏把面板放大成居中浮层，复选框列位置
会挪）。量过了 —— **不是**：居中版式的方框位置是
576/816/1053/1293 × (410/481/553/608)，和贴边版式的
580/818/1058/1296 × (462/486/558/614) 差 ≤6px，照旧坐标点得到。

真正的原因是**游戏不在前台**：游戏不是前台时会忽略鼠标输入 ——
`Mouse.click` 照样「成功」，但状态一点没变。而 `Mouse` 不带游戏窗口
句柄时，消息是发给**当前前台窗口**的：终端/控制台压着游戏时，点全落在
那个窗口上（实测终端压着游戏时点「筛选」，变化 12% 其实是终端自己在变）。

改了两处：

1. `Mouse` 带游戏窗口句柄（`core/server.py` 的定位路径之前漏了，
   `core/engine.py` 一直是对的）—— 点击直接送到游戏窗口。
2. `nav.click()` 每次点击都校验游戏在前台（`expect_foreground`）——
   不在前台就明确报「目标窗口不在前台」，而不是事后让人猜「状态不对」。
