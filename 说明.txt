SJZ 抢购控制台 · 使用说明
========================

双击 start.bat，直接弹出桌面窗口（不打开浏览器，也没有黑框）。
关掉窗口就是退出。出问题先看同目录的 desktop.log。

想用浏览器调界面（改完刷新就行，不用重启）：在目录里执行
  .venv\Scripts\python.exe run.py
然后开 http://127.0.0.1:8777


零、必须用管理员权限运行（重要）
--------------------------------
游戏如果是以管理员权限跑的，控制台也**必须**是管理员权限，
否则 Windows 会把控制台发出去的鼠标键盘消息**全部拦掉，而且一声不吭**。

症状是：点游戏里任何东西都没反应，按 F4 也没反应 —— 看起来像程序坏了，
其实是被系统拦了。

控制台启动时会自己检查：游戏权限比自己高就弹一次 UAC、用管理员身份
重开自己（点「是」就行）。万一 UAC 被拒了，手动来一次：
右键 start.bat →「以管理员身份运行」，或者右键 pythonw.exe →「以管理员身份运行」。

启动前检查里也有「程序权限」这一项，它不过就别开抢 —— 抢了也是白抢。


界面四个页签：抢购 / 队列 / 记录 / 设置。下面按用到的顺序说。


一、抢购页（一屏干完）
----------------------

最上面一条是「当前目标」：

  · 右边两个下拉：先选赛季，再选皮肤。**选完立刻生效**，不用再点「设为目标」。
  · 「清除」清掉目标，回到「抢所有挂单」。
  · 右边是「开始抢购 / 停止」——全程序只有这一个开始入口（F7 是它的快捷键）。

下面一行是抢购条件（只有这一份，改完自动存，不用点保存）：

  抢购方式          「列表捡漏」符合条件就买，不等公示期；
                    「倒计时抢购」盯公示期，归零就抢。
  品阶              极品 / 优品（在售页筛选面板的「稀有度」，不是典藏外观的品阶目录）
  成色              S / A / B / C
  价格              最低 ~ 最高（三角币）。必须填上限 —— 不填等于全档位乱抢。
  数量              这一轮抢够几件就收工（默认 1 件）
  预算              这一轮最多花多少三角币，0 = 不限

再下面是**状态条**，一行字，永远在：

  · 待机时显示最后一条日志；
  · 运行中显示「运行中 · 状态 · 最后一条日志」；
  · **启动失败时显示原因，而且会停在那里十几秒**（以前这条信息会被每秒
    一次的刷新盖掉，看起来就是「点了没反应」——这是老版本最坑的地方）。

状态条下面是实时挂单表：抢购时这里滚动显示列表里扫到的货（名称 / 成色 /
价格 / 位置）。最底下一栏是扫描次数、频率、已买件数。

最下面是「运行日志」，点标题栏可以收起 / 展开。程序为什么停、为什么换下
一件、哪一步没过，都写在这里。


1.1 启动前检查（在设置页）
--------------------------

六项，进设置页就能看到，每项一个小胶囊，✓ 通过 / ! 警告 / ✗ 拦住：

  游戏窗口   分辨率要和配置里的基准一致（默认 1920×1080）——
             所有坐标都是按基准量的；实测尺寸按比例比对，
             容差见 config.json 的 screen.base_size / screen.tolerance
  OCR 识别   PP-OCR 服务起没起（见第九节，没起会告诉你那条命令）
  时间校准   **只警告、不拦** —— 偏差是补偿掉的，倒计时那条路线不看挂钟。
             没校过时也能抢，只是定时开卖那种玩法建议先校一下。
  列表区域   交易行「在售」那块框好了没有
  程序权限   控制台必须和游戏一样是管理员权限（见上面第零节）—— 这条会拦
  游戏页面   必须站在「在售」页（不在也会自动导航过去，只警告）

没过的那几项会列在下面一行。改好之后点「重新检查」。


1.2 队列页
----------

抢购页的条件会**自动**同步成一条任务，不用手动加。这一页只是给你看：
现在排了什么、跑到哪一步、已抢几件 / 花了多少、成功还是失败（失败会写
一句原因）。「启用」勾掉这条就不跑，「删」把它连同模板一起删掉。

它抢的是什么
------------
盯的是公示期挂单的倒计时：归零那一刻货就能买。

  · 先把游戏切到「只显示公示期」，扫列表前两张卡（列表默认按解锁时间
    排序，前两张就是等得最短的），逐件点开读它的价格和倒计时
  · 按你填的价格区间挑：不在区间里的直接跳过
  · 提前 5 秒开始点（等归零是跟所有人同一刻抢，早几秒反而稳）
  · 抢到就点「跳过」回到列表，接着挑下一件；连着三件都没抢到就停
  · 抢失败会刷新列表重新挑 —— 公示期随时可能解锁，刷新才看得到新的

另一种走法（抢购方式选「在售列表捡漏」，或 config.json 里的
"workflow" 不是 "countdown" 时）：
盯「在售」页已经能买的货，把价格区间、材质、颜色、分类填进游戏的
筛选面板再点确定，设完读回来比对 —— 读回来的值比要的宽就当场停，
筛错档位宁可不抢。
游戏把下限抬到它自己的最低价（要 1000 可能变成 2050）算正常，
只会筛得更窄。
捡漏按你选的顺序挑（价格从低到高 / 磨损从低到高 / 屏幕顺序），
符合条件就点进去买，不等公示期。

"workflow" 决定走哪条路线：

  countdown  盯公示期倒计时，归零就买（控制台默认走这条）
  list       盯在售列表，谁先符合条件就买谁
  detail     盯某个商品页上的购买按钮，按钮变了就买

这一项**任务说了算**：加任务时写死了哪条路线就一直是哪条，
改全局配置不会把已经排好的任务拐到别的路线上去。

限量和预算怎么算
----------------
抢够「本轮限量」件就收工。抢的过程中累计花费，剩下的货只要超预算
就整行跳过 —— 不会点进去才发现买不起。

停了再启动，接着干
------------------
关掉控制台再打开，任务还在，条件也还在：

  · 抢购条件（价格区间 / 限量 / 预算）填完就存进 config.json，
    重开自动填回去
  · 队列里的任务存在 config.json 里，重开还在；上次没跑完的
    （进程被强杀、机器断电）会自动放回队列，不会卡在「正在抢」永远不跑
  · 改条件时是**改同一条任务**，不是删了重建 —— 「已抢 N 件 / 已花多少」
    不会归零（限量 2 件的任务否则会因此多买一件）
  · 框选区域、按钮模板、成交记录、成交截图都在，不受影响

会丢的只有「这一轮进行到哪一步」：倒计时的相位锁定、已经试过哪几件，
重启后重新扫一遍重新锁。所以**正在开点的时候别杀进程**，那一下是最贵的。

余额不足会自己停
----------------
点完购买如果弹的是「您当前的三角币不足，是否前往充值？」，程序只点
左边那个「取消」，然后停掉整场 —— 它绝不会点「充值」。

急停
----
鼠标甩到屏幕左上角 = 立刻停。抢购时手别放那儿。
（config.json 里的 failsafe，默认开着；没开的话鼠标被抢只会中止，
不会乱点，但也停不下来。）

点击频率 50 Hz
--------------
实测能跑到 1400+ Hz，但游戏 UI 有自己的响应节流，50 Hz 已经足够，
太高反而可能被判定异常。

输入通道：Interception 驱动
--------------------------
点击/按键/滚轮默认走 **Interception 内核驱动**（Oblita 官方，家用免费）：
驱动把事件从 kbdclass/mouclass 层注入，游戏读到的是真实硬件事件 ——
不再需要「SetCursorPos + PostMessage」那套组合拳，单次点击从 ~130ms
降到亚毫秒级。

* 驱动没装也不挡开工：程序自动退回旧输入方式，启动前检查的
  「输入驱动」一项会亮黄灯提醒（不拦截）。
* 装驱动：管理员运行 `tools\interception\install-interception.exe install`，
  装完**重启一次**才生效。卸载：同目录 `install-interception.exe uninstall`
  再重启。
* config.json 里 `"input_mode"`：`interception`（默认）/ `legacy`
  （强制走旧 PostMessage 路径）。


二、记录页
----------

每一次尝试都记一行：时间、结果、商品、价格、耗时。
抢到的那次还有「看图」，点开就是当时那一屏。

上面四张卡是汇总：

  抢到（件）   成交了几件
  花费         花了多少
  尝试（次）   一共试了几次
  命中率       抢到 / 尝试

命中率的分母是「尝试次数」，不是「成功次数」—— 只报成功会让人以为每次都成。

左边表格点一行，右边出详情（含当时的截图）。
「清空」只清列表，data/shots/ 里的截图不删 —— 那是证据。

成交后存截图（设置页 › 成交后存截图）
--------------------------------------
抢到一件就把当时那一屏存进 data/shots/时间_商品名.jpg。
事后翻这张图就能确认到底买到了什么、多少钱。
一张约 300KB，抢得多可以关掉。

记录和截图写在 exe 同级目录（打包成 exe 后也是），不会随程序退出消失。


三、设置页
----------

环境
  六项检查（见 1.1）+ 两个按钮：「重新检查」「时间校准」。
  没过的那几项会列在下面一行，写清楚是为什么。

开关
  按分组折叠的一片开关，拨一下立刻生效，不用重启。每一项都对应引擎真读
  的配置 —— 完整清单见第十四节。

高级
  「关注 / 取消关注」：给交易行当前选中的那件挂单点星标。抢购进行中不让点
  （两边一起动鼠标会点到别处）。


四、区域坐标和模板（已内置，不用手动框）
------------------------------------------------
引擎要知道盯屏幕上哪几块。9 个区域的坐标已经按 1080p 客户区写好默认值，
换分辨率、窗口化、系统缩放都按「实际游戏客户区」等比换算，买家不用再
自己拖框。

开抢前程序会自动标定一次：在购买按钮、确认按钮、价格、倒计时几处做模板
匹配或 OCR，确认坐标没跑偏。

  · 通过：静默继续，不打扰你；
  · 有偏移但能对上：自动按偏移量微调后继续；
  · 调完仍对不上：降级成保守坐标（四周内缩 5%），界面明确提示
    「自动标定未通过，已用保守坐标」，并说明是哪几个锚点没对上；
  · 画面里一个锚点都没看到（比如还不在交易行页面）：沿用内置坐标，
    不报错。

「设置 → 自动标定」里有一个「一键自动标定」按钮，只是手动再跑一遍；
真正需要手动拖框的情况很少，入口收在「设置 → 高级设置 → 区域微调」，
默认收起，进去后仍然是原来的抓画面、拖框、恢复默认、保存。

9 个区域（config.json 的 "regions"，值是 0~1 的归一化坐标，x/y 左上角，
w/h 宽高）：

  buy        购买按钮
  confirm    确认按钮
  list       在售列表
  clock      公示期倒计时
  bar        详情价格
  name       商品名称
  price      价格文字
  list_item  列表购买项（第一张卡片整体）
  toast      顶部提示条

所有区域都参与自动标定的锚点校验，所以都可以在高级设置里微调，不存在
「框了也不生效」的项。恢复默认 = 回到内置坐标。

templates/ 目录里放两张图：

  buy.png      「购买」按钮的样子（占位状态）
  confirm.png  确认按钮的样子

程序靠模板判断按钮有没有变、对不对得上。换完模板要重启程序（模板是启动
时读的）；区域在界面里保存后不用重启，下一次开抢自动用新坐标。


四点五、config.json 里的其它参数
----------------------------------
界面管不到的都在 config.json 里，常用的几个：

  workflow         走哪条路线：countdown / list / detail（默认 countdown）
  trigger_mode     详情页路线里怎么判断按钮变了：vanish（等占位按钮消失）
                   / appear（等可购买按钮出现）
  threshold        多像才算数，默认 0.85。太低会误触发，太高会漏
  click_hz         每秒点几下，默认 50。再高容易被游戏判定异常
  fire_timeout_s   等确认弹窗最多等几秒，默认 8
  arm_grace_s      到点还没见到占位按钮时，宽限多久直接开点，默认 1.5
  failsafe         鼠标甩左上角急停，默认开
  list_max_tries   一页最多试几条挂单，默认 20
  save_shots       成交后存截图（设置页里也能开关）
  monitor          用哪块显示器（0 起）

改完这些不用重启程序 —— 每次开抢都会重新读一次配置。


五、识别是怎么做的
------------------

列表扫描不是把整屏丢给 OCR（卡片里的字比卡片之间的缝还宽，词距一聚类就串行）。
是三步：

  1. 找框   OpenCV 在列表区域里找「够长的直线」，竖线配横线围出每张卡片的矩形
  2. 切条   每张卡里找出「有字的那几条横带」（枪的图案太高，按高度筛掉），放大 3 倍
  3. 认字   Windows 自带 OCR 逐条认，再按内容归类：带「成色」的是成色、
            带数字的是价格、最长带中文的是名称

为什么不按固定位置切：同一张卡有两种版式 —— 能买的卡把成色和价格印在上面、
名称在下面，公示中的卡反过来。按位置写死必然切错一种。

价格可以是一位数（真机真有 2 个三角币的挂单），但名称里的 M4A1 不会被
当成价格 —— 名称那条带永远不参与价格判定。

相邻帧逐卡比对：只有真的变了的那张卡才重新认字，其余直接用上一帧的结果
（实测同一帧 750ms → 16ms）。列表刷新、翻页之后要重认（程序里会自动清缓存）。

倒计时掐得准不准
----------------
不是等「0分0秒」—— 那一整秒里真实剩余可能是 0.99 秒，最坏晚整整一秒。
程序按「跳秒的时刻」反推归零时刻：看到显示值变成 S，就得到归零 ≈ 看到它
的时刻 + S，再加 1 秒（实测这版界面是 floor，取整方式是实测标定过的）。


六、砖皮知识库（内部用，界面上没有入口）
-----------------------------------------
core/bricks.json 里存着两类东西：

  1. **典藏砖皮**：11 个赛季的砖皮 —— 赛季、武器型号、砖皮名、别名、
     当期还是往期、做工（极品/优品）、成色（S/A/B/C）和磨损区间。
  2. **品阶目录**（2026-10-23 真机采集）：每个赛季 × 四个品阶
     （传说 / 史诗 / 稀有 / 普通）下的**全部皮肤**（含你已拥有的和
     没拥有的），每件都记着：**出自哪个赛季、哪个品阶、哪个枪种、
     哪把枪**。

第 2 份是「要抢某一砖」用的：游戏里每个系列都有四个品阶的皮肤，
典藏外观页的筛选面板就是按「系列 + 品阶 + 枪种」过滤的。

**界面上怎么用**：顶栏「典藏外观」页 —— 左边选赛季，右边选品阶和枪种，
点某一件就「定位 + 标记」：
  · 定位 = 机器人在游戏里设好筛选（系列 / 品阶 / 枪种）、滚到列表、
    点中那一张，并把标题栏读回来核对
  · 标记 = 记成当前目标（存在 config.json 里），抢购页会显示「抢哪一件」，
    引擎会优先去这一件，而不是列表里的第一件

按名字找一件砖（`bricks.find_skin`）：模糊匹配 —— 游戏用花体字，
OCR 常把「彩」认成「采/未/米」、「白」认成「自」，武器型号里的「-」
认成「·」，所以比对前会去掉所有分隔符再比相似度。

枪种有两层：筛选面板上是七档（步枪 / 冲锋枪 / 霰弹枪 / 轻机枪 /
精准射手步枪 / 狙击步枪 / 手枪），皮肤名里更细（突击步枪 / 战斗步枪 /
射手步枪 / 通用机枪…）。目录里两个都记着（`gun` 和 `gun_fine`）。

排序是：极品 S（隐藏模板）> 极品 S > 极品 A > 优品 S > … > C 级。
「当期」和「往期」也影响价值：超过 5 个赛季的砖进入稀有掉落，存量少。

两个容易踩的坑（知识库里也写了）：
  · S10 的砖皮是「群星 - AKM」，不是网上攻略写的「SR-3M 深渊之核」。
  · 「群星」一名两用：S10 的砖皮叫群星，S11 的赛季名也叫群星。
    认砖皮看武器型号：群星 = AKM，疾光魅影 = MK4。


七、遇到问题
------------

「还没框选购买按钮区域」   → config.json 里补 buy 区域和 templates/buy.png。
「列表模式要先框选交易行列表区域」 → config.json 里补 list 区域。
「5 秒内没看到占位按钮」   → 界面不在公示中状态，或模板截错了状态。
「鼠标被抢」               → 有别的东西在动鼠标（含你自己的手），
                            程序会立刻中止，避免点到别处。重开一次即可。
「到点了但没看到占位按钮」 → 你在开卖之后才点开始。程序会宽限 1.5 秒
                            后直接开点，但这时候已经晚了，尽量提前布防。
「公示期里没有符合条件、还在倒计时的商品」
                          → 筛选区间里现在没有货，或者没站在「在售」页。
「OCR 认不出商品名」       → 名称区域框太松，或字号太小。框紧一点。
「F7 按了没反应」          → 看日志：多半是启动前检查没过，日志里写了哪几项。


八、文件说明
-------------

九、OCR：PaddleOCR PP-OCRv6（唯一后端）
--------------------------------------
程序里所有读字的地方（商品名、价格、成色、倒计时、判断停在哪个页面）
都走 core/ocr.py，底下只有一个后端：本机的 PaddleX OCR 服务跑
PP-OCRv6 small。

为什么是它
  2026-11-01 拿 data/shots 里的真截图切出 42 个字段（商品名 / 成色 /
  价格 × 1x2x3x 放大）逐个判分，同一批图喂给所有候选：

    引擎                        字段准确   整屏 1380×630   1920×1080
    Windows OCR（原来的）        16/42       66ms        118ms / 价格 0/6
    PaddleOCR-VL-1.6              漏块     161s(CPU)         —
    RapidOCR v6 small            31/42      264ms            —
    RapidOCR v5 server           40/42     2159ms            —
    PP-OCRv5 server              42/42      192ms            —
    PP-OCRv5 mobile              42/42       95ms            —
    PP-OCRv6 small               42/42       63ms        98ms / 价格 6/6

  PP-OCRv6 small 是唯一「准确率满分 + 延迟可接受」的。其它方案（Windows
  自带 OCR、PaddleOCR-VL、RapidOCR）连同代码一起删了 —— 少一层选择，
  就少一处「换后端导致点击落点偏移」的隐患。

  真机分辨率那一列很关键：到了 1920×1080，PP-OCR 不但更准，还比 Windows
  OCR 更快（98ms vs 118ms）。Windows OCR 在整屏上连一个价格都读不对
  （`25,開0`、`9，000`）。

怎么起 OCR 服务（一次性，装在独立环境里）
  1. 建环境（别装进 .venv —— 那个要打包 exe，paddle 进去包会大十倍）
       py -3.11 -m venv .venv-vl
       .venv-vl\Scripts\python.exe -m pip install paddlepaddle-gpu==3.3.1 ^
           -i https://www.paddlepaddle.org.cn/packages/stable/cu126/
       .venv-vl\Scripts\python.exe -m pip install "paddleocr[doc-parser]"
       .venv-vl\Scripts\paddlex.exe --install serving
  2. 起服务（首次会下模型，之后秒开）
       .venv-vl\Scripts\paddlex.exe --serve --pipeline tools\OCR_game.yaml ^
           --port 8081 --device gpu:0
     显存约 0.5GB，游戏开着也能一起跑。
     卡不够就把 --device gpu:0 去掉走 CPU —— 但 CPU 上一次要几秒，不建议。
  3. 看自检：desktop.log 开头的「OCR 后端 = ...」应当写着
       PaddleOCR PP-OCRv6 small（HTTP http://127.0.0.1:8081/ocr）· 实测 xxms/次
     那行会带实测延迟 —— 超过 400ms 说明在跑 CPU 或显卡被占满了。

  tools\OCR_game.yaml 是给游戏界面调的产线配置，和默认配置差三处：
  关掉文档方向分类/去弯曲（对游戏截图纯属浪费，整屏 306ms → 150ms）、
  关掉响应里的可视化图（默认每张图多传 630KB 无用数据）、用 v6 small 权重。

服务不用你手动起了（2026-11-02 起）
  控制台启动时会自己把 OCR 服务拉起来，并一直盯着它：
    · 定时重启：默认每 6 小时一次（ocr.service.restart_hours）
    · 变慢就重启：最近 20 次识别的中位耗时超过 800ms（ocr.service.slow_ms）
    · 挂了就重启：探活失败立即重起
  重启是**蓝绿**的：先在备用端口（8081/8082 轮换）起一个新实例，等它真能
  认字了再把客户端切过去，最后才杀老的 —— 切换过程中调用方一次都不会失败。
  实测（本机 3070，游戏开着）：切换 8~14 秒，期间 60 次识别 0 失败。
  正在抢购的那一轮里不会重启，会等它跑完（最多等 10 分钟）。

  启动前检查里那行会显示「服务已跑 X.Xh，重启 N 次」，一眼能看出管家在干活。

服务没起会怎样（比如 .venv-vl 没装）
  启动前检查的「OCR 识别」那项不过 → 不许开抢，并直接给出起服务的命令。
  宁可开不了工，也不要带着瞎的眼睛去抢。
  运行中服务挂了：识别返回空 → 引擎按它已有的失败分支处理（报「读不出
  倒计时」或跳过该商品），不会乱点。连续 3 次失败后客户端会停用 10 分钟，
  避免每 5 秒白等一次超时。

config.json 的 ocr.ppocr 里能调：url（换机器换端口）、timeout_s（单次超时，
默认 5 秒）、max_side（超过这个边长先缩图再发）、cache（同图缓存条数，
页面识别会反复看同一张图，命中就不花时间）、min_score（低于这个置信度的
行丢掉）。

想自己复跑评测（换了模型/换了显卡之后应该重跑一次）
    .venv-vl\Scripts\python.exe tools\ocr_eval.py --engine ppocr_v6_small --json %TEMP%\p.json
    .venv\Scripts\python.exe    tools\ocr_eval.py --engine winrt --json %TEMP%\w.json
    .venv\Scripts\python.exe    tools\ocr_eval.py --compare %TEMP%\w.json %TEMP%\p.json


十、找皮肤：从全库定位某一件
----------------------------
典藏外观页没有搜索框，只能靠「筛 + 滚 + 认」。这段逻辑在
core/skinfind.py，抢购（引擎）和界面上的「定位」按钮走的都是它。

每件皮肤「怎么点」：core/skins_raw.csv
  官方概率公示整理的 243 件，字段是 皮肤名/枪械型号/枪种/品阶/赛季/系列。
  程序从它算出筛选面板上该点哪儿，规则在 core/skinfilter.py：

    赛季下拉   选这个赛季对应的砖名（S1→棱镜攻势、S10→群星…共 11 个）
    品阶       第几个框：传说=0 史诗=1 稀有=2 普通=3（典藏外观的品阶目录；
               在售页筛选的「稀有度」是另一套，只有 极品 / 优品）
    枪种       官方 8 种并成面板上的 7 个框：
               突击步枪 / 战斗步枪 → 步枪     冲锋枪 → 冲锋枪
               霰弹枪 → 霰弹枪                轻机枪 → 轻机枪
               射手步枪 → 精准射手步枪        狙击步枪 → 狙击步枪
               手枪 → 手枪

  自检：`python -c "from core import skinfilter, bricks; print(skinfilter.verify(bricks.catalog()))"`
  返回 ok=True 表示 243 件全部能算出点哪儿、而且和知识库一一对得上。

三步走
  0. 先看当前这一屏（不动任何筛选）
     抢购前你通常已经把这件选好了，这时候只要确认一眼 —— 几百毫秒。
     找不到才往下走。
  1. 按「赛季+品阶+枪种」筛，再滚着找
     三样都按上表的规则点，列表通常只剩一两件，一屏就翻完。
     **只有当表里这个组合确实有货时才筛** —— 筛出空列表会让面板变成
     居中浮层（见下面「为什么」），所以动手前先查表计数。

     筛选是**先读后点**：一次截图读出 14 个勾选框的当前状态（亮像素判断，
     不用 OCR），和目标的差集才点。状态本来就对时一个框都不点；
     赛季下拉也先读一眼，已经是目标就跳过重选（选一次要滚 3 屏、每屏一次
     OCR）。实测这一步把筛选耗时从 112 秒压到 31 秒。
  1.5 只按赛季筛（组合筛不到时退到这一档）
  2. 全库扫（兜底）
     赛季也筛不到（知识库记错了赛季），就不筛任何条件，从头翻到底。
     243 件全库大约 35 屏 —— 慢，但一定翻得到。

为什么只按赛季筛、不按品阶/枪种筛
  游戏在**筛出空列表**的时候，会把筛选面板从「贴左边」变成「屏幕中央
  的浮层」，坐标整体右移下移、行距也变大（品阶勾选框从 x=580/818/1058/
  1296 变成 636/906/1176/1436）。而复位逻辑用的是贴边坐标 —— 一旦筛空，
  后面所有点击全部落空，流程卡死，只能重启游戏。
  只按赛季筛永远不会空（每个赛季都有皮肤），面板就永远是贴边布局。
  代价是多扫几屏，一屏 7 张、OCR 几百毫秒，划算。

怎么认「是不是它」
  列表里的名字会被游戏截断（「AK-12突…」），所以不能拿列表名当准。
  真正的判据是**点开这张卡、读右边的大标题**，和目标名做相似度比对
  （阈值 0.72）。OCR 认错一个字也扛得住（实测「电玩高手」被读成
  「电玩高丢」，相似度 0.93，照样认对）。
  列表名只用来**粗筛**：型号（QBZ95 / AS Val）对不上的卡，连点都不点。

实测（2026-11-02，1920×1080）
  第一屏就有    AKM突击步枪-群星     找到，1 屏 1 次点击
  要往下滚      K416突击步枪-命运    找到，2 屏 2 次点击
  要换赛季      M4A1突击步枪-棱镜攻势  找到（筛到赛季后只剩一张卡）
  耗时：筛选阶段是大头（复位要点十几个框、选赛季要滚下拉），
  单件 1~2 分钟；OCR 服务快的时候（150ms/次）能压到 10 秒内。
  显卡被游戏占满时 OCR 会慢到 2~5 秒/次，整条流程跟着变慢 —— 这是
  硬件争用，不是逻辑问题。

接口
  POST /api/skins/locate {"name": "..."}
    返回 {ok, y, title, score, plan, screens, tried, elapsed_s}
    plan 告诉你最后是哪一档找到的（当前屏 / 赛季 XX / 全库扫描）


十一、关注（收藏）某件挂单
------------------------------
交易行右侧详情面板顶部有个星标（标题右边、放大镜左边）：

    坐标 (1754, 239)   金色 = 已关注，灰白 = 未关注

判据用**颜色**不用 OCR —— 星只有 14px，OCR 认不出；金色 R 比 B 高 130 左右，
灰白基本相等。取色时只统计框里的**亮像素**：取样框大部分是深色底，直接
取全框平均会把 R-B 从 135 稀释到 43，判成「未关注」（这个坑踩过）。

代码：`nav.follow_state()` 读、`nav.set_follow(want)` 写（状态已经对就不点）。
接口：`POST /api/follow {"want": true|false}`，设置页 › 高级里有「关注 /
取消关注」两个按钮。

实测（2026-11-02）：点一下从灰白变金色，diff 19；API 走 `关注→取消→再关注`
三步状态都对（before/after 都返回）。

注意：这是**交易行**详情面板上的星（关注某件挂单）。典藏外观页右上角那个
「★我的关注」(1689,197) 是另一个入口 —— 进去看已关注的列表。


十二、任务清单（按顺序执行）
------------------------------
清单页把多个目标排成一列，按顺序跑：**筛选 → 定位 → 倒计时 → 购买**。

    勾选框   取消勾选的任务会被跳过（引擎跑之前过滤 enabled）
    #        执行顺序：手动任务（无开卖时间）永远排在最前，其余按开卖时间
    目标     皮肤名；空名 = 不按名字过滤（抢所有挂单）
    条件     价格区间 · 品阶 · 成色 · 数量 · 预算 · 抢购方式
    状态     等待 / 布防 / 运行中 / 完成 / 失败 / 跳过

三个按钮：清空已完成（删任务在每一行右边）。任务不用手动加 —— 抢购页点
「开始抢购」时会自动把当前目标和条件同步成一条。

接口：GET /api/tasks，POST /api/tasks/add|update|remove|clear。
注意 `enabled` 必须能通过 update 改 —— 以前白名单里没有它，界面点了没反应。


十三、控制台界面（2026-11-03 精简）
------------------------------------
上一版是三栏：顶栏 + 左侧竖排导航 + 右栏一大片设置。同一个功能有多个入口，
条件在三个地方各填一遍（筛选行、右栏、设置页开关），实测最容易出「界面写
2000、实际按 111 抢」这种事。这一版砍成**一屏一入口**：

    顶栏    品牌 / 页签（抢购·队列·记录·设置）/ 状态胶囊（游戏·OCR·权限）
            —— 顶栏同时是窗口拖拽区（无边框窗口只能拖这里）
    抢购页  任务条（当前目标 + 赛季/皮肤下拉 + 开始/停止）
            筛选行（方式 / 品阶 / 成色 / 价格 / 数量 / 预算）—— 唯一一份
            状态条（一行，启动失败的原因停在这里十几秒）
            实时挂单表 + 表尾（扫描次数 / 频率 / 已买 / 条数）
            运行日志（可折叠）
    队列页  只读的执行队列 + 清空已完成
    记录页  成交记录
    设置页  环境检查（六项胶囊 + 重新检查 / 时间校准）
            开关（按分组折叠）
            高级（关注 / 取消关注）
    底栏    连接状态 / OCR / 校准 / F7 提示 / 时间 / 版本

这一版删掉的东西（都是重复入口或死 UI）
  · 左侧竖排导航 —— 和顶栏页签完全重复
  · 右栏「执行模式」单件/多件/全自动 —— 前端记了这个值，后端从来没读过
  · 右栏「价格与数量」—— 和筛选行是同一份值，靠 bindPair 双向同步
  · 右栏「成色胶囊」—— 和筛选行的成色下拉是同一份值
  · 「应用条件」按钮 —— 现在改完自动存（防抖 600ms）
  · 右栏「开始抢购」大按钮、「开始执行」按钮 —— 全程序只留一个开始入口
  · 「把当前目标加进清单」—— 开始抢购时自动同步
  · 「设为目标」按钮 —— 下拉选完就是目标

几个约定
  · 条件只有一份，改哪都是它；「开始抢购」先存条件、再把目标 + 条件写进
    队列（/api/tasks/add|update），最后调 /api/scheduler/start。不写队列的话
    引擎跑的是上一次的条件，界面上改的等于白改。
  · 表格数据来自引擎最近一屏的扫描结果（engine.status()["rows"]），
    每秒刷新一次；没开抢时是空的，属正常。
  · 顶部三个胶囊来自启动前检查（/api/preflight）：游戏窗口、OCR、程序权限。
  · 状态条是「启动失败」唯一的出口：以前错误写进状态栏、紧接着被每秒一次的
    轮询覆盖回「空闲」，用户看到的就是「点了没反应」。现在它带 hold 时间，
    轮询不会盖掉。
  · 页面加 `?frozen=1` 只跑一轮、不开定时轮询（自动化探测 / 截图用）。

前端就一个文件 web/index.html，没有外部依赖（不引 CDN、不引图标库），
打包时整目录带进 exe。改完用 tools/probe_frontend.py 验过：脚本能跑通、
开关/环境检查/状态条/日志区都渲染出来、点「开始抢购」的失败原因留得住。


十四、开关表：41 个开关，每一个都真的有用
------------------------------------------
设置页那一片开关来自 core/switches.py 的一张表。每一项都写着三件事：
**开关 → 配置点路径 → 谁在读它**。界面上拨一下写进 config.json，引擎下次
start 重新读配置，立刻生效，不用重启。

分组（共 40 项）
  运行模式   半自动、抢购路线
  收藏设置   抢前先关注、抢到后取消、关注重试、关注后等待、已关注不重复点
  价格与筛选 最低价、最高价、每轮限量、总预算、做工、最大磨损、挑单顺序
  抢购设置   点击频率、识别阈值、连点超时、确认连点、确认间隔、
             购买延迟、随机抖动、延迟自适应、成交校验
  自动与停止 扫描间隔、扫描总时长、最多试几件、详情页等待、没抢到换下一件、
             抢到就停、连续失败停、停止热键、开抢热键
  截前       休市截前、截前热键
  环境与安全 开点前抢前台、启动前检查、成交截图、写成交记录、
             防误触、输入通道

怎么保证「不是假开关」
  tests/test_switches.py 里有一条静态检查：把 core/ 下所有源码拼起来，
  逐个开关找它的消费点（配置叶子名或 switches.get 的 key），找不到就
  判失败。想在表里加一行装样子，测试直接红。
  另外还钉住：默认值必须和 config.DEFAULTS 一致（不一致的后果是界面显示
  「开」、引擎读到「关」）。

几个值得单独说的
  半自动      定位、筛选、进详情全做，停在购买按钮前，最后一下留给你按
  购买延迟    解锁瞬间先等 N 毫秒再开点（按钮还没画出来时点也是白点）
  延迟自适应  按上一轮「点下去→弹窗出现」的实测耗时反推该提前还是推后，
              每轮都记在 engine._fire_lag 里
  成交校验    点完确认必须看到结算弹窗（或余额减少）才算成交。关掉能跑，
              但记录里会标 verified=false —— 见下面第十四节
  连续失败停  连败到阈值就停，避免界面改版/被风控时空转到天亮
  抢到就停    抢到一件就停掉整条队列，而不是接着跑下一个任务
  休市截前    05:00-08:00 休市时，鼠标摆到购买键上按 F10 替你点一下

接口：GET /api/switches（分组 + 当前值）、POST /api/switches {"values":{...}}。


十五、成交判定：点完确认不等于买到了
------------------------------------
2026-11-02 修的一个洞，值得单独记一笔。

**问题**：主路径 `_fire_and_confirm` 点完确认就无条件记 hit。结果 data/
里堆了 78 条「成交」，配的截图打开一看全是交易行列表 —— 一条真的都没有。
别人先买走、余额不足、弹窗没响应，都会表现为「点了但什么都没发生」。

**现在的判据**（按顺序）：
  1. 结算弹窗出现（_bought_dialog：左边「获得枪械外观 / 拥有：N」，
     或者底部「跳过」）→ 成交
  2. 读不到弹窗时，看余额有没有减少 → 成交
  3. 都没有 → 记 miss，日志写「点了 N 下确认，但没看到结算弹窗」

记录里新增 `verified` 字段：true = 校验过的成交；false = 关掉了成交校验
（fire_verify）时「点了就算」的结果。老记录没有这个字段。

想复盘：`data/records.jsonl` 一行一条，`result` + `verified` 两列就够分清
「真抢到」和「只是点了一下」。


十六、能不能脱离人独立跑 / 能不能真买到
----------------------------------------
独立跑：能。双击 start.bat（或以管理员身份运行）→ desktop.py 起控制台
（127.0.0.1:8777）+ 内嵌窗口；OCR 服务由管家在后台自己拉起、自己重启，
不需要人守着。命令行自检：`.venv\Scripts\python.exe desktop.py --doctor`。

真买到：**还没有被验证过**，而且现在这台机器上跑不了，原因三条：
  1. 控制台必须是管理员权限。游戏是管理员权限时，普通进程发的鼠标消息
     会被 UIPI 静默丢掉 —— 点了没反应，还不报错。启动前检查里
     「程序权限」这一项会拦住。
  2. 游戏得停在交易行「在售」页（或公示期页）。停在别处时
     「游戏页面」这项检查不过。
  3. 买一次花的是真钱，没有你点头我不点。

所以现在的状态是：**识别、筛选、定位、导航、掐点、点击这些环节都有测试和
真机验证，但「确认成交」这一环从来没有成功跑通过一次**。今天之前那 78 条
「成交」是假的；今天之后，它要么真买到并留下结算弹窗的截图，要么老实记
miss。

要真验证，建议这么来（花最少的钱）：
  1. 以管理员身份运行 start.bat，把游戏停在交易行在售页
  2. 挑一件最便宜的（几百三角币的普通品质），价格区间卡死在那件附近
  3. 先打开「半自动」：它只定位到购买键前停手，检查落点对不对
  4. 再关掉半自动真跑一次，看记录里 result=hit 且 verified=true、
     并且 data/shots 里那张图是结算弹窗


十七、点击流程的速度（2026-11-03 优化）
----------------------------------------
抢购拼的就是最后那几百毫秒。先把每一段量出来，再决定改哪儿 —— 实测（本机
1920×1080，OCR 走本地服务）：

    抓确认弹窗区 340×90        1.85ms
    模板匹配                    0.25ms
    驱动点击（3 次 send_mouse） 0.01ms
    读一次倒计时（240×65 OCR）  24.7ms

结论：**截屏+匹配只要 2ms**，驱动点击几乎免费。所以任何「固定等 X 毫秒」
都是纯浪费。

改掉的三处（合计最坏 ~1.03 秒）

  1. 解锁检测  250ms 轮询 + 归零后固定 sleep(0.6)
     → 按读表成本（约 25ms）轮询，归零立刻返回。
     实测：归零 → 确认可点  **850ms → 2ms**

  2. 确认点击  盲点 20 下 × 10ms
     → 闭环：点一下看一眼弹窗还在不在，没了立刻收手；还在就继续点，
       最多点到「确认兜底时长」（默认 2s）。连点次数用完后降到 50ms 一下，
       不再 500Hz 猛砸。
     实测：弹窗第一下就关  **200ms → 10ms**
     附带好处：以前多点的 19 下会落在奖励弹窗上（那上面有「跳过」），
     现在不会了。

  3. 点击空档  两次点击之间纯 sleep(20ms)
     → 按 4ms 一个节拍继续采样弹窗。
     实测：弹窗出现在空档中间 → 被发现  **最坏 20ms → 4ms**

另外两处小改
  · 开点循环改成「睡 间隔-实际耗时」，click_hz 才真的等于配置值
    （以前每轮还要花 2.5ms 截屏，实际只有 44Hz 而不是 50Hz）
  · 列表模式「点进详情 → 等购买按钮」的采样粒度 10ms → 5ms

现在的延迟账（单次购买，从解锁那一刻算）
    解锁被感知        ~2ms（原来最多 850ms）
    点购买            ~0.01ms
    确认弹窗被感知    ~4ms（原来最多 20ms）
    点确认到成交      ~10ms（原来固定 200ms）
    ────────────────────────────
    合计              ~16ms（原来 ~1070ms）

其中「归零后 150ms 内必须返回」「空档里 20ms 内必须发现」都能直接挡住回退。
